# 关卡 3 · 归属

做完这一关，学生只能看自己的提交，教师能看全部并批改，越权访问返回真实的 403。

前两关管的是“这个角色能不能进这个门”，这一关管的是“进了门之后能碰哪条数据”。两件事不一样，实现位置也不同。

## 你手上有什么

- `contract.md` 里的归属规则、任务视图字段、30011 与 30012 两个错误码
- 前两关已经能把人分清
- `check.sh` 的第 17 到 22 条

## 要做到

| 编号 | 结果 |
| --- | --- |
| 17 | 学生提交，`owner` 是当前登录人，状态“待批改” |
| 18 | 请求体里塞别人的用户名，不生效 |
| 19 | `/api/tasks/mine` 每一条都是自己的 |
| 20 | 学生看别人的任务，真实 403 |
| 21 | 学生看自己的任务，200 |
| 22 | 教师批改后学生能看到分数，同一份不能批第二次 |

## 建议的动作顺序

1. 提交接口先跑通。这一步会暴露第 18 条：如果你直接把请求体里的字段存进库，归属就是别人说了算。
2. 写“我的提交”查询。查询条件从令牌取，不从参数取。
3. 写详情接口的归属判断。先只允许本人，跑第 20、21 条。
4. 再加教师豁免，让有批改权限的人也能看。
5. 写批改接口，注意状态流转：已批改的不能再批。

第 3 步的判断放在哪一层，是这一关的核心。

## 卡住了看这里

**第一个坎：归属判断写在了控制层**

功能是对的，测试也能过，但换一种调用方式就绕过了。

提示：控制层只该收参数、调服务、返结果。业务规则放服务层，凡是要判断“这一行归谁”的，都在服务层。想一个具体后果：以后加一个“导出学生提交”的接口，是不是还得把同一段判断再抄一遍。

**第二个坎：服务层怎么知道当前是谁**

要判断归属，服务层得知道登录人。两种做法：从安全上下文静态取，或者从参数传进来。

提示：静态取会让服务层依赖安全框架的线程状态，写单元测试时要先伪造上下文。传参更麻烦一点，但服务层干净。选哪个都行，写进你的 SPEC，别中途改。

**第三个坎：教师也 403**

只写了“owner 等于当前用户”，忘了有批改权限的人该放行。

提示：判断条件是“本人 或者 有某个权限点”，两个条件取或。看第 21 条之后，让 teacher01 也访问同一条，确认两边都通。

**第四个坎：提交时 owner 是空的**

请求体里没有 owner 字段，直接存库就是 null。

提示：归属不来自请求体，来自令牌。这一条和第一个坎是同一件事的两面。

**第五个坎：重复批改没拦住**

同一份任务能被批两次，分数来回改。业务码 30012 是给这个场景的。

提示：批改前先读状态，已批改的直接抛业务异常，别让它更新。

## 过关标准

第 17 到 22 条全过。另外手动验证越权：

```bash
TOKEN=$(curl -s -X POST http://127.0.0.1:8009/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"student01","password":"Student#2026"}' \
  --noproxy '*' | python3 -c 'import sys,json;print(json.load(sys.stdin)["data"]["token"])')

# 种子数据里 id=1 是 student01 自己那条，200
curl -i -H "Authorization: Bearer $TOKEN" http://127.0.0.1:8009/api/tasks/1 --noproxy '*'

# id=2 是 student02 的，403
curl -i -H "Authorization: Bearer $TOKEN" http://127.0.0.1:8009/api/tasks/2 --noproxy '*'
```

两条的响应体都应该是 JSON，不是 HTML。
