# 图的选型与要素清单

软件工程文档里画错图，多半不是画工问题，而是一开始选错了图形。
下面先按「想表达什么」定位图形，再逐张给出必备要素和常见错法。

## 一、按表达目的选图

| 想表达的内容 | 用哪张图 | 不该用 |
| --- | --- | --- |
| 系统由哪些层次、哪些服务组成，彼此怎么依赖 | 系统架构图 | 部署图（那是物理机器的事）、流程图 |
| 系统外的谁，能做什么事 | 用例图 | 功能模块图（那是系统内部结构） |
| 系统内部拆成哪些功能模块，层级关系如何 | 功能模块图 | 用例图 |
| 一次交互中，对象之间按时间发生的消息 | 时序图 | 活动图（活动图不强调对象） |
| 一个对象在生命周期里的状态与迁移条件 | 状态图 | 流程图（流程图关注步骤，不关注状态） |
| 业务流程、操作步骤、谁负责哪一步 | 活动图 | 时序图 |
| 程序内部判断、循环、处理顺序 | 流程图 | 活动图（活动图属于 UML，流程图是结构化方法） |
| 数据有哪些实体、属性，实体之间什么联系 | E-R 图 | 类图（类图有方法，E-R 没有） |
| 软件装在哪些机器上、网络怎么连 | 部署图 | 架构图（架构图不落到物理节点） |
| 项目排期、任务依赖、里程碑 | 甘特图 | 流程图 |
| 类的属性方法、继承实现关系 | 类图 | E-R 图 |

三条容易混的界线：

- **架构图 vs 部署图**：架构图讲「逻辑分层」，部署图讲「物理落地」。架构图里出现「阿里云 ECS」「192.168.1.10」就是串了；部署图里出现「业务逻辑层」也是串了。
- **活动图 vs 流程图**：活动图有泳道、有分叉汇合条、属于 UML 行为图；流程图是结构化方法的工具，只有处理、判断、输入输出。课程设计报告里两者都被接受，但同一份文档里不要混用两套符号。
- **用例图 vs 功能模块图**：用例图站在系统外看系统能做什么，画的是「谁—能做什么」；功能模块图站在系统内看模块怎么拆，画的是「父—子」。用功能模块图代替用例图是学生作业里最常见的错误。

## 二、每张图的要素清单

### 系统架构图

必需：
- 分层（表现层 / 接入层 / 业务层 / 数据层，或按 C4 分成容器层、组件层）
- 每层内的模块名称，以及模块的职责一句话
- 层与层之间的依赖方向（单向向下，不要画成双向箭头）
- 用到的关键技术（Vue 3、Spring Boot、MySQL），写在模块里，不要单独漂浮在画面上

常见错法：
- 把所有技术名词堆成一堆方框，不体现层次
- 画成双向箭头，读者看不出调用方向
- 端口号、IP 出现在架构图里
- 缺少数据层，业务模块直接连到空白处

画法：`scripts/build_templates.py` 的 `architecture()`，或直接改 `assets/templates/svg-architecture.svg`。

### 用例图

必需：
- 系统边界矩形，名字写在框内顶部
- 参与者（火柴人），画在边界外，左右都行
- 用例（椭圆），画在边界内
- 参与者与用例之间的实线关联
- 非平凡关系要标：`«include»`（被包含的用例必然执行）、`«extend»`（在特定条件下追加）、泛化（空心三角箭头）

常见错法：
- 参与者画在系统边界内
- 用动词短语以外的名字（「用户管理模块」是模块名，不是用例；用例应写「管理用户」）
- 所有用例连所有参与者，画成蜘蛛网
- 把 `include` 和 `extend` 的箭头方向画反（都是箭头指向被包含/被扩展的用例）
- 一张图塞 20 个用例。超过 12 个就按角色或子系统拆图

画法：`assets/templates/svg-usecase.svg`，坐标规律见 `svg-cookbook.md`。

### 功能模块图

必需：
- 根节点＝系统名
- 一级模块（3～6 个），横向排开
- 二级功能挂在对应模块下方，从属关系靠连线体现，不靠位置猜
- 同一层的方框尺寸统一，视觉上不出现大小混排

常见错法：
- 二级功能没有全部挂在父节点下，出现「孤儿节点」
- 用菱形、椭圆混排（这张图只用矩形）
- 层级超过三级。三级以上改用树形表格或分图

画法：`assets/templates/svg-module.svg`。这条主干 + 引线的连法是关键，
不要用「父节点直接拉一条斜线到每个子节点」，斜线一多就乱。

### 时序图

必需：
- 参与者在顶部，从左到右按调用顺序排列（用户 → 前端 → 网关 → 服务 → 存储）
- 生命线（竖直虚线）
- 同步调用：实线 + 实心箭头；返回：虚线 + 空心箭头
- 激活条（矩形窄条），表示对象正在处理请求
- 分支用 `alt` / `else`，循环用 `loop`，可选流程用 `opt`，并行用 `par`
- 消息文字写「做什么」，接口调用可以带上方法和路径

常见错法：
- 所有消息都用实线实心箭头，分不清调用和返回
- 没有激活条，看不出谁在处理
- 分支写成两条平行线，读者不知道互斥
- 把 UI 文案（「点击按钮」）和接口调用混在同一层粒度
- 参与者超过 7 个，画布塞不下，应拆图

画法：Mermaid `sequenceDiagram`，模板 `assets/templates/mmd-sequence.mmd`。

### 状态图

必需：
- 唯一的初态（实心圆 `[*]`）
- 至少一个终态（双圆）
- 状态用圆角矩形，名字用形容词或完成态（「待审核」「已通过」），不要用动词短语
- 迁移箭头上写「事件 [守卫条件] / 动作」
- 状态多于 8 个时，用复合状态分层

常见错法：
- 状态名写成动作（「提交申请」是事件，不是状态）
- 漏掉终态，状态机永远不结束
- 箭头没有触发事件，只有一根光秃秃的线
- 所有状态两两互连，画成蜘蛛网。这时该拆复合状态

画法：Mermaid `stateDiagram-v2`，模板 `assets/templates/mmd-state.mmd`。

### 活动图

必需：
- 开始节点（实心圆）和结束节点（双圆，表示整个活动结束）
- 活动用圆角矩形
- 判断用菱形，出边标条件
- 泳道（可选但推荐），一条泳道对应一个角色或系统
- 并行活动用分叉/汇合

常见错法：
- 泳道之间来回跳，箭头交叉成乱麻
- 把「结束」画成单个圆（那是初态）
- 判断只有一条出边，另一条悬空
- 把活动图画成时序图（活动图没有对象概念）

画法：Mermaid 没有活动图语法，用 `flowchart TD` + `subgraph` 泳道表达，
模板 `assets/templates/mmd-activity.mmd`。

### E-R 图

分两种，别混：

**概念模型（Chen 记号）**——课程作业、需求规格说明书用这种
- 实体：矩形；弱实体：双线矩形
- 属性：椭圆；主键属性加下划线；多值属性加双线椭圆
- 联系：菱形，边上标 1 / n / m
- 没有外键、没有字段类型

**物理模型（表结构）**——数据库设计文档用这种
- 表名 + 字段 + 类型 + PK/FK/UK
- 关系用连线 + 基数符号（`||--o{` 读作「左边 1 条对右边 0..N 条」）

常见错法：
- 概念模型里写 `varchar(50)`，那是物理模型
- 概念模型漏掉主键下划线
- 基数标注只在一边写，另一边空着
- 多对多联系直接连成 m:n，没有拆出中间实体（物理模型里必须拆）

画法：概念模型用 `assets/templates/svg-er.svg`；物理模型用 Mermaid `erDiagram`，
模板 `assets/templates/mmd-er-physical.mmd`。

### 部署图

必需：
- 节点（3D 立方体），标 `«device»`（客户端设备）或 `«node»`（服务器）
- 节点内写运行时环境（JDK 21、Spring Boot 3.3、MySQL 8）
- 节点之间的通信路径，标注协议和端口（HTTPS 443、JDBC 3306）
- 执行环境（如 Tomcat 集群）用外框把多个实例包起来

常见错法：
- 节点里写业务模块名（「课程服务」是逻辑组件，不是部署单元；部署单元是「app-01」）
- 通信路径不标协议和端口
- 缺少客户端设备节点
- 一个节点里塞进整个系统

画法：`assets/templates/svg-deployment.svg`。

### 流程图

必需：
- 开始/结束用圆角矩形（或椭圆）
- 处理用矩形，判断用菱形，输入输出用平行四边形，数据存储用圆柱
- 判断的每条出边都写条件
- 主流程从上到下，回退线走外侧

常见错法：
- 判断出边不写「是/否」，读者不知道哪条走哪边
- 回退线从节点中间穿过
- 节点超过 15 个还画在一张图里，Mermaid 会排成细长条
- 把流程图当活动图用，加泳道

画法：Mermaid `flowchart`，模板 `assets/templates/mmd-flowchart.mmd`。

### 甘特图

必需：
- 标题、时间格式、时间轴刻度格式
- 任务分组（section）
- 任务起止时间，依赖用 `after` 表达而不是手填日期
- 里程碑（持续 0 天）
- 关键路径任务标 `crit`

常见错法：
- 所有任务手写绝对日期，改一处就要改全部（应该用 `after`）
- 刻度按天排，一屏几百条竖线（用 `tickInterval 1week`）
- 任务名过长，溢出到任务条上（版本库名控制在 10 字内，或调大 `leftPadding`）

画法：Mermaid `gantt`，模板 `assets/templates/mmd-gantt.mmd`。

### 类图

必需：
- 类框三段：类名 / 属性 / 方法
- 可见性符号：`+` public、`-` private、`#` protected、`~` package
- 关系：实线三角箭头＝继承，虚线三角箭头＝实现，实线实心菱形＝组合，实线空心菱形＝聚合
- 多重性标注（`1`、`0..*`）

常见错法：
- 继承画成普通箭头，看不出是继承还是关联
- 属性和方法写在一起，不分段
- 把所有类都画上，一张图 30 个类。应只画核心领域模型

画法：Mermaid `classDiagram`，模板 `assets/templates/mmd-class.mmd`。

## 三、交付前自检

画完逐条对一遍，能挡掉大部分返工。

1. 图的类型和文档章节标题对得上吗（「系统设计」章节里出现用例图就是串了）
2. 图里出现的每个名词，正文里都有解释吗
3. 有没有指向不明的箭头、悬空节点
4. 文字有没有被线穿过、被框裁掉
5. 图题、图号、正文引用（「如图 3-2 所示」）都齐了吗
6. 黑白打印一遍，还能分清层次和连线吗
7. 缩到 A4 页宽时，最小的字还看得清吗（小于 10px 就要改）
