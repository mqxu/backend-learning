## 1 目标回顾

本章回答：立项时承诺了什么、边界划在哪里、最终是否兑现。

### 1.1 建设目标

项目立项时确定四个目标：

1. **一个后端、三个入口**：用一套 Spring Boot 服务同时支撑微信小程序（学生与组织者）和管理后台（团委审核员/管理员），避免三套后端重复实现权限与业务规则。
2. **一条完整链路**：学生发现活动 → 报名（含审核、候补、取消）→ 现场扫码签到 → 组织者统计；组织者发布 → 提审 → 团委审核 → 发布；管理员管理活动与用户并留痕。
3. **规则正确可验证**：名额不超卖、重复报名被拦、候补按序转正、签到码不可伪造、越权操作被拒，且这些结论有可重复执行的验证手段。
4. **可演示、可交付**：任何一台装有 JDK 21、MySQL 8、Node 18+ 的电脑，按 README 五步即可跑起来；课程设计文档齐全、图表可打印。

### 1.2 范围边界

V1 明确**不做**以下内容，避免范围蔓延：微信支付与报名费、微信订阅消息模板（仅站内消息）、文件上传（活动封面使用外链字段，演示数据为空）、地图选点（经纬度由种子数据或手填提供）、多租户与细粒度数据权限。这些能力在 1.3 节列为后续改进方向，不在本期承诺范围内。

## 4 技术亮点

本章回答：这个项目在哪些地方做得比「能跑就行」更进一步。选取六个有代码支撑、且直接对应业务正确性的设计点，每点给出关键片段与设计意图。

### 4.1 条件 UPDATE 占名额，不做「先查后写」

报名最怕超卖。常见写法是先 `select` 查剩余名额，再 `update` 加一，两个请求并发时都能查到「还有 1 个名额」，最终卖出 2 个。本项目把判断写进 SQL 的 `WHERE` 里，用影响行数判断结果：

```java
@Update("""
        UPDATE activity
           SET signed_count = signed_count + 1
         WHERE id = #{activityId}
           AND deleted = 0
           AND (capacity = 0 OR signed_count < capacity)
        """)
int occupySeat(@Param("activityId") Long activityId);
```

调用方只认返回值，等于 1 才算占到名额，否则走候补或报满员：

```java
} else if (activityMapper.occupySeat(activityId) == 1) {
    target = SignupStatus.SUCCESS;
} else if (activity.waitlistOn()) {
    target = SignupStatus.WAITLIST;
} else {
    throw new BizException(ResultCode.SIGNUP_FULL);
}
```

这样一条 SQL 就是一次原子判断，不需要分布式锁；`capacity = 0` 表示不限人数的分支也放进同一条件里，避免额外分支。重复报名再用 `uk_activity_user` 唯一索引兜底，`DuplicateKeyException` 统一转成「你已报名该活动」。

### 4.2 候补队列：占位成功才转正

满员后进入候补，取消时按序号取队首转正。关键点是「释放名额」与「转正」必须在同一事务里，且转正前必须真正占到名额，否则会出现候补显示成功但名额没了的假转正：

```java
ActivitySignup next = signupMapper.findFirstWaitlist(activityId);
if (next == null) {
    return;
}
if (activityMapper.occupySeat(activityId) != 1) {
    return;
}
next.setStatus(SignupStatus.SUCCESS.getCode());
signupMapper.updateById(next);
```

候补序号用 `max(waitlist_seq) + 1` 生成，排队顺序稳定；转正成功后发「候补转正成功」站内消息。若占位失败（例如同时有人抢先），本次不转正，等下一次释放再触发，宁可少转也不产生负名额。

### 4.3 HMAC 动态签到码，不落库、可容错

签到码不是随机数，而是 `activityId + 时间片 + HMAC-SHA256(activityId:slice) 前 16 位` 拼成的三段式字符串，服务端只保存密钥，不保存码。生成与校验都只依赖时间片，因此天然防篡改：

```java
public String generate(Long activityId) {
    long slice = currentSlice();
    return activityId + "." + slice + "." + sign(activityId, slice);
}

for (int i = 0; i <= toleranceSlices; i++) {
    long candidate = now - i;
    if (candidate == slice && sign(activityId, candidate).equals(parts[2])) {
        return activityId;
    }
}
throw new BizException(ResultCode.CHECKIN_TOKEN_INVALID);
```

时间片默认 30 秒，校验时接受最近 2 个历史片，既容许手机与服务器的秒级时钟差，也把「截图转发」的有效期限制在约 90 秒内。再叠加报名状态校验、签到窗口校验与「扫码 + 定位」的 200 米校验，形成多层防线。

### 4.4 注解式鉴权：Controller 声明意图，拦截器统一执行

权限不写在每个方法里，而是用 `@RequireLogin`、`@RequireRole` 声明在类或方法上，由拦截器统一解析 JWT 并校验。未标注登录的公开接口也允许携带 token，从而在同一接口上返回「我的报名状态」等个性化字段：

```java
boolean needLogin = handlerMethod.hasMethodAnnotation(RequireLogin.class)
        || handlerMethod.getBeanType().isAnnotationPresent(RequireLogin.class);
if (needLogin && current == null) {
    writeError(response, HttpServletResponse.SC_UNAUTHORIZED, ResultCode.UNAUTHORIZED);
    return false;
}
RequireRole requireRole = handlerMethod.getMethodAnnotation(RequireRole.class);
if (requireRole != null) {
    boolean allowed = Arrays.stream(requireRole.value()).anyMatch(r -> r.equals(current.role()));
    ...
}
```

控制器上只需一行声明，例如 `@RequireLogin` 加 `@RequireRole({"REVIEWER", "ADMIN"})`。角色之外的归属校验（只能操作自己创建的活动）放在服务层 `requireOwnActivity`/`requireManage`，因为「是不是我的活动」必须查库，不适合放拦截器。

### 4.5 审计留痕：关键动作写前后状态

审核、下架/取消、补签、角色变更四类动作都会写入 `audit_record`，记录业务类型、业务 ID、动作、操作人、变更前后状态与备注。后台「操作日志」页直接展示这张表，形成可追溯链路：

```java
AuditRecord record = new AuditRecord();
record.setBizType("USER");
record.setBizId(userId);
record.setAction("ROLE_CHANGE");
record.setOperatorId(operator.id());
record.setOperatorName(operator.nickname());
record.setBeforeStatus(before);
record.setAfterStatus(role);
auditRecordMapper.insert(record);
```

审计记录与业务更新在同一事务中提交，业务成功则留痕必然成功，避免「改了但没记录」。这也是课程设计里「可追责」的具体落地：谁能证明某场活动是被谁下架的？看日志页即可。

### 4.6 三端 VO 裁剪：不把实体直接丢给前端

后端对外返回的是 VO 而不是实体，按场景裁剪字段并做格式化。列表页只要摘要信息，详情页才给正文与报名表单；用户信息按「是否绑定」决定学籍字段是否有值：

```java
public static ActivityItemVO of(Activity activity, String categoryName, String orgName) {
    ActivityItemVO vo = new ActivityItemVO();
    vo.setTitle(activity.getTitle());
    vo.setStartTime(DateTimes.formatMinute(activity.getStartTime()));
    vo.setStatusLabel(ActivityStatus.of(activity.getStatus()).getLabel());
    vo.setSignupOpen(isSignupOpen(activity));
    return vo;
}
```

这样做有三个好处：时间统一格式化为字符串，前端不用处理时区；状态同时给 `status` 与 `statusLabel`，前端不做字典映射；敏感或无用字段（如删除标记、密钥）不会泄露。`UserVO` 里 `bound` 字段由 `studentProfile` 是否存在推导，前端据此决定是否展示「去绑定」，避免前端自己拼业务判断。

## 5 难点与解决

本章回答：开发过程中真正卡住过的地方、怎么解决的、留下了什么经验。

### 5.1 名额并发与整批审核的回滚

难点：报名与「组织者批量通过」都会占名额，批量通过时如果第 3 个人名额不足，前 2 个已经占用的名额必须回滚，否则名额被吃掉但报名没通过。

解决：整段审核逻辑放在 `@Transactional` 方法里，占位失败直接抛 `BizException`，事务回滚已占名额；错误信息写「名额不足，无法通过全部报名」，让组织者知道是整批失败而不是部分成功。代价是批量通过要么全成要么全败，对课程设计场景足够。

### 5.2 候补转正与取消的时序

难点：取消报名要「释放名额 → 找队首 → 占位 → 改状态 → 发消息」五步，任何一步顺序不对都会出现负名额或重复转正。

解决：五步放在取消的同一事务里，先释放再占位，占位失败就不转正；候补序号单调递增，队首查询按 `waitlist_seq` 升序取第一条。消息在状态更新之后发送，即使消息发送失败也不影响名额正确性。

### 5.3 签到码的防伪造与时钟偏移

难点：如果签到码是固定值，截图转发即可代签；如果严格按秒校验，手机与服务器差几秒就签不上。

解决：用 HMAC + 30 秒时间片，服务端接受最近 2 个历史片；校验顺序固定为「码是否有效 → 活动是否存在 → 是否仅手动签到 → 是否在窗口 → 是否报名 → 是否已签到 → 是否报名成功 → 定位是否在范围内」。顺序固定后，错误提示才能准确指向原因（40001/40002/40003/40004/40005）。

### 5.4 权限归属：注解管角色，服务层管归属

难点：`@RequireRole` 只能判断「是不是组织者」，判断不了「这场活动是不是他创建的」；如果只靠前端隐藏按钮，越权请求仍可成功。

解决：拦截器负责登录与角色，服务层每个写操作都调用 `requireOwnActivity` 或 `requireManage`，校验 `creator_id` 与当前用户，管理员例外放行。这样即使有人直接构造请求，也会返回 20003「只能操作本组织的活动」。

### 5.5 时间与时区的一致性

难点：MySQL、JVM、前端三方时区不一致时，活动时间会整体偏移 8 小时；`LocalDateTime` 与 `Date` 混用也会导致序列化格式不统一。

解决：数据源连接串固定 `serverTimezone=Asia/Shanghai`，Jackson 统一 `yyyy-MM-dd HH:mm:ss` 与 `Asia/Shanghai`；VO 输出统一用 `DateTimes.formatMinute` 转字符串；`data.sql` 用 `CURDATE()`、`NOW()` 生成相对时间，避免硬编码日期在不同机器上错位。

### 5.6 演示数据「隔天就废」

难点：课程设计演示往往在导入数据几天后进行，硬编码日期的活动全部过期，首页空空如也，评审现场很尴尬。

解决：种子数据全部用相对时间；同时增加 `DevDataInitializer`，在 `dev-mode` 下检测「是否所有已发布/进行中/已结束活动都已过期」，是则整体平移到未来并重置为已发布。这个设计只用于开发演示，生产环境不启用，并在文档中写明数据时间基准。

## 7 经验总结

本章回答：如果再做一次，哪些做法要保留、哪些要避免。

1. **先定事实基线，再并行写文档。** 接口数、表数、状态码、角色名这些口径如果每份文档各写一套，最后合并时必然冲突。本项目先用一份写作基线锁定数字与术语，再分头写 12 份文档，交叉检查成本大幅下降。
2. **用「状态机 + 规则编号」约束实现。** 活动 7 态、报名 7 态的迁移条件与 18 条业务规则先编号，实现时逐条对照，测试时逐条断言。规则一旦有编号，「实现了没有」就从主观判断变成可勾选清单。
3. **并发正确性交给数据库，不交给应用层假设。** 条件 UPDATE、唯一索引、事务回滚三件套能解决大部分超卖与重复问题，比在 Java 里加锁更简单也更可靠。
4. **接口契约先行，三端才能并行。** 开发阶段先定路径、入参、出参与错误码，前端用假数据先写页面，后端按契约实现，联调时问题集中在字段与状态而不是「接口还没写」。
5. **冒烟脚本是交付门槛，不是可选项。** 20 项断言把「登录→建活动→审核→报名→候补→签到→统计」串成一条可重复执行的验收线，任何人改动后跑一遍就知道有没有破坏主链路。
6. **演示数据要「保鲜」，文档要写清时间基准。** 相对时间 + 启动平移解决了「隔天演示全过期」的尴尬；同时把这一点写进部署与操作手册，避免使用者以为数据坏了。
7. **诚实记录范围裁剪。** 编辑入口、订阅消息、支付这些没做的内容，在总结与待确认事项里写清楚，比含糊带过更有利于后续维护，也避免答辩时被问到却无法解释。
