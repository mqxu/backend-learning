## 1. 写作规范

1. **事实口径**：数字、名称、状态码、接口路径、表名、角色名一律以本基线为准，不自创同义词。
2. **不编造**：不写性能实测值、用户量、并发量、第三方版本以外的服务能力。课程设计里允许写「目标值」并标注「设计目标」，不得写成「实测」。
3. **章节编号**：一级 `1.`，二级 `1.1`，三级 `1.1.1`，不超过三级。每章开头用一句话说明「本章回答什么问题」。
4. **图表编号**：图题写在图下方，格式 `图 X-N 名称`；表题写在表上方，格式 `表 X-N 名称`；X 为文档编号。正文必须先「如图 X-N 所示」再放图。
5. **引用编号**：功能 `FR-*`、规则 `BR-*`、接口 `API-*`、数据表 `T-*`，首次出现给全称，后续用编号。
6. **表格优先**：能表格化的不写长段落；单段不超过 6 行。
7. **代码片段**：只保留能说明设计的关键片段（≤20 行），必须来自真实源码，可省略无关行但不得改写逻辑。
8. **术语统一**：见第 3 节术语表，全文一致；不混用「用户/账号」「活动/项目」「核销/签到」。
9. **文档头**：每份文档开头放信息表和版本记录；结尾放「待确认事项」（没有就写「无」）。
10. **语言**：简体中文，客观陈述，不用营销词（「极致」「赋能」「遥遥领先」），不用第一人称。

## 3. 术语表

| 术语 | 英文/代码 | 含义 |
| --- | --- | --- |
| 用户 | `sys_user` | 学生、组织者、后台账号共用一张表，用 `role` 区分 |
| 学籍档案 | `student_profile` | 绑定成功后写入的学号、姓名、学院、年级、专业 |

| 报名记录 | `activity_signup` | 一个用户对一场活动的唯一报名记录 |
| 签到记录 | `activity_checkin` | 一次实际签到，与报名记录一对一 |
| 名额占用 | `signed_count` | 活动已占用的名额数，报名成功/签到/未到场时占用 |
| 候补 | waitlist | 满员后按序号排队，有人取消时队首转正 |
| 签到码 | checkin token | HMAC 签名的动态二维码内容，30 秒轮换，不落库 |

| 未到场 | `NO_SHOW` | 活动结束后，报名成功但未签到的记录 |
| 时间片 | slice | 签到码的 30 秒有效期单位 |
| 逻辑删除 | `deleted` | 0 正常、1 删除，MyBatis-Plus 自动过滤 |
| 雪花 ID | `assign_id` | 应用层生成的 BIGINT 主键，非自增 |
| 审核 | audit | 团委对活动的发布审核，以及组织者对报名的审核 |

## 4. 角色与权限

| 角色 | 入口 | 认证方式 | 能做 | 不能做 |
| --- | --- | --- | --- | --- |
| STUDENT 学生 | 小程序 | 微信登录（dev 模式 mock openid） | 浏览、报名、取消、签到、消息、收藏 | 发布活动、审核、后台登录 |
| ORGANIZER 组织者 | 小程序 | 同学生，角色为 ORGANIZER 且绑定组织 | 本组织活动增删改、提审、报名审核、签到核销、统计 | 审核活动发布、管理用户 |
| REVIEWER 审核员 | 管理后台 | 账号密码 | 活动审核、活动管理、看日志与工作台 | 改用户角色 |
| ADMIN 管理员 | 管理后台 | 账号密码 | 全部后台能力，含用户角色变更、组织列表 | — |

权限实现：`@RequireLogin` 校验登录；`@RequireRole` 校验角色；服务层再做「活动创建人 = 当前用户 或 管理员」的归属校验。`/api/app/**` 的查询类接口允许匿名访问，登录后额外返回个性化字段（我的报名状态、是否收藏）。

## 8. 业务规则

| 编号 | 规则 |
| --- | --- |
| BR-01 | 报名前必须已绑定学籍（`student_profile` 存在），否则返回 10003 |
| BR-02 | 仅 `PUBLISHED` 状态的活动可报名，且须落在 `[signup_start_time, signup_end_time]` 窗口内 |
| BR-03 | 名额占用用单条条件 UPDATE：`capacity = 0 OR signed_count < capacity`；影响行数为 0 即满员，不做「先查后写」 |
| BR-04 | 满员时若开启候补，进入 `WAITLIST` 并取 `max(waitlist_seq)+1`；未开启返回 30001 |
| BR-05 | 取消报名释放名额后，按 `waitlist_seq` 取队首候补，占位成功才转正，转正发消息 |
| BR-06 | 同一活动同一用户唯一（`uk_activity_user`）；已取消/审核未通过可重新报名，其余状态重复提交返回 30002 |
| BR-07 | 活动开启报名审核时先进入 `PENDING`；组织者通过时逐个占名额，名额不足则整批报错 |
| BR-08 | `PENDING/SUCCESS/WAITLIST` 可取消；超过 `cancel_deadline` 拒绝；`SUCCESS/CHECKED_IN/NO_SHOW` 占用名额 |
| BR-09 | 签到窗口为活动开始前 30 分钟至结束后 30 分钟，可配置 |
| BR-10 | 扫码签到校验顺序：签到码有效 → 活动存在 → 非「仅手动」→ 在窗口内 → 已报名 → 未签到 → 状态为 SUCCESS → 定位 ≤200 米（checkin_type=2） |
| BR-11 | 重复签到由 `uk_signup` 唯一索引与状态判断双重拦截 |
| BR-12 | 时间约束：活动开始 < 结束；报名开始 ≤ 报名结束 ≤ 活动开始；取消截止 ≤ 活动开始（缺省为开始前 2 小时） |
| BR-13 | 状态推进：到开始时间 PUBLISHED → ONGOING；到结束时间 PUBLISHED/ONGOING → FINISHED，同时 SUCCESS → NO_SHOW |
| BR-14 | 已发布/进行中的活动被编辑后回到 PENDING，防止绕过审核修改时间地点 |
| BR-15 | 组织者只能操作自己创建的活动（服务层校验 creator_id），管理员可跨组织操作 |
| BR-16 | 学号绑定：学号须在白名单内，一个学号只能绑定一个微信，绑定后白名单 `used_flag=1` |
| BR-17 | 签到码 = `activityId + "." + slice + "." + HMAC-SHA256(activityId:slice) 前 16 位`，不落库；服务端接受最近 3 个时间片 |
| BR-18 | 逻辑删除仅用于 `sys_user`、`organization`、`activity` 三张表（`deleted` 字段，MyBatis-Plus 自动过滤）；其余 9 张表无删除字段，不做逻辑删除 |
