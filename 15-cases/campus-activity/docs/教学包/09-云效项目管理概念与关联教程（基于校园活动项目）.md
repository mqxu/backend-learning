# 云效项目管理概念速通（以「校园活动小程序」为例）

> 面向 4 次课的学生小组：用 10 分钟把 **里程碑、迭代、需求、任务、工作项、工时** 和它们之间的关联讲清楚。所有例子都来自本课程项目 `校园活动小程序-课程模板`，数据截至 2026-11-11。

## 0. 一句话总览

云效 Projex 里，**工作项是统称**；**需求/任务/缺陷**是工作项的不同类型；**迭代**是装任务的时间盒；**里程碑**是带日期的检查点；**工时**是任务上的人力投入；**关联**把“为什么做、做什么、谁来做、什么时候做、做得怎样”串起来。

```
项目：校园活动小程序-课程模板
│
├── 需求 REQ-01 … REQ-08          “为什么做 / 做成什么样”
│        │  关联项（ASSOCIATED）
│        ▼
├── 任务 CA-01 … CA-25            “具体做什么”
│        │  迭代字段
│        ├──────────────► Sprint 1（第 1–2 次课，14 条任务）
│        └──────────────► Sprint 2（第 3–4 次课，11 任务 + 8 缺陷）
│
├── 缺陷 DEF-01 … DEF-08          “哪里做错了 / 怎么修”
│
├── 里程碑 M1 … M4                “到哪个日期必须交付什么”
│
└── 工时：预计 / 实际 / 迭代容量    “花了多少人力和时间”
```

## 1. 六个概念，一张表

| 概念 | 一句话解释 | 本项目中的例子 | 容易混淆的点 |
| --- | --- | --- | --- |
| **工作项** | 云效里所有可跟踪事项的统称，有类型、状态、负责人、优先级等字段 | 本项目共 **41 条工作项**：8 需求 + 25 任务 + 8 缺陷 | 工作项 ≠ 任务；任务只是工作项的一种 |
| **需求** | 描述“用户/业务要什么”，重点是价值与验收标准 | `REQ-03 报名与名额`：报名、取消、候补、防超卖；验收“名额不超卖、重复报名 30002” | 需求不是“大任务”，不直接拆到某一天做 |
| **任务** | 可执行、可估时、可一天内推进完的工作 | `CA-15 报名与名额并发控制`、`CA-17 签到码生成与扫码签到` | 任务要能落到“谁、哪天、做什么” |
| **缺陷** | 与预期不一致的问题，记录现象/原因/修复 | `DEF-04 上传 bizType 重复导致 50001` | 缺陷不是需求；修完要回写关联的需求/任务 |
| **迭代** | 固定长度的时间盒（Sprint），盒子里装任务并统计完成度 | `Sprint 1`（第 1–2 次课）、`Sprint 2`（第 3–4 次课） | 迭代 ≠ 里程碑；迭代是“时间段”，里程碑是“检查点” |
| **里程碑** | 项目中的关键日期节点，用来对齐“到点交付什么” | `M1 环境与骨架就绪`（11-12）→ `M4 上线与答辩`（11-30） | 里程碑不装任务；它靠日期和验收标准约束迭代 |
| **工时** | 任务上的人力投入：预计工时、实际工时、迭代容量 | `CA-15` 预计 8h、实际 6h；`Sprint 1` 容量按 4 人 × 8h 估算 | 工时 ≠ 工期；工时是“投入”，工期是“日历跨度” |

## 2. 六个概念怎么配合：用一条业务链走一遍

以“报名”这条链为例：

1. **需求**：`REQ-03 报名与名额`——学生能报名、取消，满员进候补，不能超卖。
2. **任务**：把需求拆成 `CA-15 报名与名额并发控制`、`CA-16 候补队列与转正`。
3. **迭代**：这两条任务放进 `Sprint 1`，和登录、活动、Security 等 14 条任务一起，构成第 1–2 次课的交付范围。
4. **工时**：`CA-15` 预计 8h，组内后端同学认领；完成后登记实际 6h。
5. **关联**：`CA-15`、`CA-16` 通过“关联项”挂到 `REQ-03`；`REQ-03` 详情页就能看到 2 条关联任务。
6. **缺陷**：测试发现“并发报名超卖”，记 `DEF-0x`，关联到 `REQ-03`/`CA-15`，修复后关闭。
7. **里程碑**：`M2 核心业务闭环`（11-19）检查 `REQ-03` 是否验收通过——通过则里程碑达成，否则迭代顺延并在站会说明。

## 3. 各类关联，分别解决什么问题

| 关联 | 云效里的位置 | 本项目实例 | 作用 |
| --- | --- | --- | --- |
| **需求 ↔ 任务** | 工作项详情 → 关联项（ASSOCIATED） | `REQ-03` ↔ `CA-15`、`CA-16`；全项目共 **33 条**需求-任务/缺陷关联 | 回答“这个任务为什么做”；需求页能汇总进度 |
| **任务 ↔ 迭代** | 任务详情 → 迭代 字段 | `CA-01～CA-14` → `Sprint 1`；`CA-15～CA-25` + 8 缺陷 → `Sprint 2` | 回答“什么时候做”；形成迭代看板与燃尽图 |
| **缺陷 ↔ 需求/任务** | 缺陷详情 → 关联项 | `DEF-04` ↔ `REQ-06`/`CA-21`；`DEF-01/02/08` ↔ `REQ-08` | 回答“问题影响哪个需求”；验收时一并检查 |
| **任务 ↔ 任务** | 工作项详情 → 依赖项（阻塞/被阻塞） | 建议：`CA-03 建库` 阻塞 `CA-07 实体/Mapper`；`CA-10 Security` 阻塞 `CA-11 学号绑定` | 回答“先后顺序”；防止并行做错 |
| **需求 ↔ 代码** | Codeup 提交/MR 描述写任务号 | 提交信息 `feat(activity): ... (CA-12)`；`v1.0.0` tag | 回答“哪行代码实现了哪个任务”；可追溯 |
| **需求 ↔ 测试** | Testhub 用例关联工作项 | 报名/候补/签到用例关联 `REQ-03/REQ-04` | 回答“怎么证明做对了”；测试计划按需求组织 |
| **人 ↔ 工作项** | 负责人 / 参与人 / 抄送 | 每组按后端、前端、测试、DevOps 分工 | 回答“谁负责、谁配合、谁知晓” |

> 关键区别：**关联项（ASSOCIATED）** 是“平级引用”，**子项/父项** 是“层级拆解”。本课程统一用“关联项”表达需求与任务的对应关系，避免把需求做成任务的父级后统计口径混乱。

## 4. 里程碑和迭代到底差在哪

| 对比项 | 迭代 Sprint | 里程碑 Milestone |
| --- | --- | --- |
| 本质 | 固定长度的时间盒 | 带日期的关键节点 |
| 装什么 | 任务、缺陷 | 不装任务，只做验收标记 |
| 时间 | 有开始/结束日期，可滚动 | 一个计划完成日期 |
| 本项目 | Sprint 1：第 1–2 次课；Sprint 2：第 3–4 次课 | M1 环境与骨架（11-12）、M2 核心业务（11-19）、M3 双端联调（11-26）、M4 上线与答辩（11-30） |
| 怎么用 | 站会看看板、看燃尽 | 到点验收检查点 C1–C6，未达成要说明原因与补救 |

一句话：**迭代管“节奏”，里程碑管“节点”**。一个里程碑可以跨一个迭代，也可以落在迭代中间；不要用里程碑代替迭代排期，也不要用迭代代替里程碑验收。

## 6. 五个常见误区

1. **把迭代当里程碑**：迭代是时间盒，里程碑是验收点。Sprint 2 结束不等于 M4 自动达成，要按检查点验收。
2. **把需求当任务**：需求写“为什么/验收”，任务写“具体动作+估时”。`REQ-03` 不是任务，`CA-15/CA-16` 才是。
3. **把工作项只当任务**：工作项是统称，需求、任务、缺陷、风险都是工作项；筛选“工作项”时会看到全部 41 条。
4. **把关联项当子项**：关联项是平级引用，子项是层级拆解；本课程统一用关联项，统计“需求关联了多少任务”更直接。
5. **把工时当工期**：预计 8h 不代表要 8 天；它用于排容量和看负载，实际工时用于复盘估算准确度。

## 7. 课堂 10 分钟练习

以 `REQ-03 报名与名额` 为例，小组一起完成：

1. 打开需求详情，确认验收标准（不超卖、重复报名 30002、候补顺序正确）；
2. 在“关联项”里挂上 `CA-15`、`CA-16`；
3. 给两条任务填“预计工时”（如 8h、6h）并挂到 `Sprint 1`；
4. 在依赖项里加“`CA-03` 阻塞 `CA-07`”这类先后关系（至少 1 条）；
5. 到 `Sprint 1` 看板确认任务已出现，到 `M2` 里程碑确认验收日期；
6. 找一个已修缺陷，检查它是否关联到对应需求/任务。

完成标准：需求有 ≥1 条关联任务、任务有迭代和预计工时、看板能看到任务、里程碑有日期和验收人。

## 9. 命名与填写规范（本项目约定）

- 需求：`REQ-<两位序号> <动词+对象>`，如 `REQ-03 报名与名额`；描述必须含“验收标准”。
- 任务：`CA-<两位序号> <动作+对象>`，如 `CA-15 报名与名额并发控制`；描述含“做什么 + 验收”。
- 缺陷：`DEF-<两位序号> <现象>`，如 `DEF-04 上传 bizType 重复导致 50001`；描述含“现象/原因/修复”。
- 里程碑：`M<序号> <节点名>` + 计划完成日期 + 验收人。
- 迭代：`Sprint 1` / `Sprint 2`，描述写清“覆盖哪几次课、目标是什么”。
- 提交/MR：`feat|fix|test|docs(scope): 说明 (CA-xx)`，便于从代码反查任务。

---

**一句话记住**：需求说“为什么”，任务说“做什么”，迭代说“什么时候做”，里程碑说“到点交付什么”，工时说“投入多少”，关联把六者串成一条可追溯的链。
