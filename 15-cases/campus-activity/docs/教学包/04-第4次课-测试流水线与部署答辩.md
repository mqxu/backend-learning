### 1.1 本课在课程中的位置

前三次课分别完成「后端跑通 → 业务闭环 → 双端联调」。本课完成最后一步：**把能跑的系统变成可交付的版本**——测试有证据、构建可重复、部署可回滚、答辩讲得清。

> 第 1 次能启动 → 第 2 次能跑通 → 第 3 次能演示 → **本课能交付、能答辩**。

### 1.2 本课一句话任务

> **「让本组代码从 `develop` 出发，经过 20 个自动化用例、33 项冒烟、一条云效流水线，变成一个公网能打开、可回滚、有发布记录的 `v1.0.0`。」**

教师开场可直接使用：

> 「前三次课我们证明『它能在我的电脑上跑』。今天要证明三件事：第一，换一台电脑也能跑；第二，别人能验证它是对的；第三，坏了能退回去。能做到这三点，这个项目才叫交付，而不是演示。」

### 2.2 教学重点

1. **两条测试命令的完整执行与解读**：`cd server && mvn -o test`（20/20）与 `./scripts/smoke.sh`（33/33）。

### 5.5 云效 Flow 流水线四阶段

表 4-13 流水线 `campus-activity-ci` 阶段

| 阶段 | 做什么 | 关键命令/配置 | 产物 | 失败常见原因 |
| --- | --- | --- | --- | --- |
| 1 测试 | 后端集成测试 | `cd server && mvn -B test`（本地等价 `mvn -o test`） | 测试报告 | MySQL/Redis 不可用；依赖未下载 |
| 2 构建 | 后端打包 + 两端构建 | `cd server && mvn -B clean package -DskipTests`；Node20 构建 `admin`、`app` | jar、`admin/dist`、`app/dist/build/h5` | 构建目录未设 `server`；Node 网络受限 |
| 3 制品上传 | 整理并归档部署包 | `ArtifactUpload`：`app.jar`、`web`、`deploy.sh` | 制品包 | 路径写错、文件缺失 |
| 4 主机部署 | 下发并重启 | `VMDeploy` → `/opt/campus-activity/package.tgz` → 解压 → `sh deploy.sh restart` | 运行中的新版本 | 主机组离线、权限、jar 启动失败 |

**YAML 流水线**：仓库提供 `deploy/flow/campus-activity-pipeline.yaml`，与界面配置等价，便于版本化和课堂复用。YAML 实际组织为 `test_stage`（单元测试，公共构建集群无 MySQL/Redis 时按文件注释跳过）→ `build_stage`（后端打包 + 两端构建 + 制品上传，多个 step 共享同一工作空间）→ `deploy_stage`（VMDeploy 主机部署）；从交付流程看仍是「测试 → 构建 → 制品 → 部署」四步。文件顶部标注 **4 个占位符**：`<REPO_NAME>`（代码库展示名称）、`<CODEUP_REPO_URL>`（Codeup 仓库地址）、`<SERVICE_CONNECTION_ID>`（服务连接 ID）、`<MACHINE_GROUP_ID>`（主机组 ID），逐项替换为本组环境的值；键名与说明以 YAML 顶部注释及 `deploy/README.md` 为准。

**降级方案（教师必讲）**：若云端无 MySQL/Redis，按 YAML 注释把 `test_stage` 跳过（或改用自建构建集群），构建阶段用 `-DskipTests`，20 用例在本地完成后把报告截图附到发布记录，口径必须是「本地 20/20、云端跳过测试」，不能把「跳过」写成「通过」；若云端 Node 构建因网络受限失败，改为「本地构建两端 → 把 `web/` 一起随制品上传」。

### 5.8 部署架构：公网只到 Nginx

```text
浏览器 / 微信客户端
        │ HTTP(S) :80/:443
        ▼
┌──────────────────────────────┐
│ ECS：Nginx                    │
│  /            → web/admin    │
│  /app/        → web/app      │
│  /api/        → 127.0.0.1:8016
│  /uploads/    → 127.0.0.1:8016
└──────────────┬───────────────┘
               ▼
        systemd：campus-activity.service
               │ java -jar /opt/campus-activity/app.jar
               ▼
        MySQL 3306 / Redis 6379（仅本机，不对公网）
```

**要点**：8016/3306/6379 不对公网开放，安全组只放行 22、80（HTTPS 则 443）；生产与开发的最大差异是**配置与入口**（Nginx 同域反代、`dev-mode=false`）；上传目录 `/opt/campus-activity/uploads` 须由 `campus` 用户可写并纳入备份。

### 5.10 发布、回滚与备份

**发布**：`develop` 合并到 `main` → 打 annotated tag `v1.0.0` → 云效发布记录关联流水线运行 → 部署到 ECS → 公网验证。

> 口径说明：云效默认方式把 `package.tgz` 直接解压到 `/opt/campus-activity/`，`app.jar` 会被新包覆盖，旧版本依赖 `releases/` 中的归档快照；更稳妥的做法是按 YAML 注释先解压到 `/opt/campus-activity/staging/` 再执行 `deploy.sh restart`，脚本会先备份运行中的旧 jar。细节见 [06 手册](06-ECS部署与运维实操手册.md) 第 8 章。

**回滚三步**：

```bash
# 1) 准备：每次发布前保留旧 jar（deploy.sh 会把发布快照归档到 releases/，发布人再核对一次）
cp /opt/campus-activity/app.jar /opt/campus-activity/releases/app-$(date +%Y%m%d%H%M).jar

# 2) 回滚：停服务 → 换回旧 jar → 重启
sh /opt/campus-activity/deploy.sh stop
cp /opt/campus-activity/releases/app-<上一版本时间>.jar /opt/campus-activity/app.jar
sh /opt/campus-activity/deploy.sh restart

# 3) 验证：探活 + 关键页面
curl -s http://127.0.0.1:8016/api/ping
```

**回滚原则**：

1. 前端回滚优先（静态目录备份，不影响后端与数据库）；后端回滚用「版本化 jar + 重启」，不在原文件覆盖。
2. 数据库回滚是最后手段：先保护性备份现场，再按发布前备份恢复；`schema.sql` 含 `DROP TABLE`，生产禁止直接重跑。
3. 每次回滚填回滚记录（时间、原因、范围、版本、数据影响、执行人、验证结果）。

### 5.11 流水线失败定位方法

```text
① 先看哪个阶段红：测试 / 构建 / 制品 / 部署
② 测试失败 → 环境（MySQL/Redis）还是断言？看第一行异常
③ 构建失败 → 工作目录是否为 server？依赖是否下载成功？Node 网络是否受限？
④ 制品失败 → 路径/文件名是否与制品清单一致？
⑤ 部署失败 → 主机组是否在线（SSH 22）？jar 能否 java -jar 启动？端口 8016 是否被占？
⑥ 部署成功但页面 502 → Nginx 与后端端口、systemd 状态、journalctl 日志
```

## 8 常见错误与排错

表 4-20 常见错误（12 条）

| 序号 | 现象 | 可能原因 | 解决办法 | 教师处理建议 |
| --- | --- | --- | --- | --- |
| 1 | `mvn -o test` 报依赖找不到 | 本地仓库缺依赖，首次用了离线模式 | 去掉 `-o` 联网拉取一次，之后恢复离线 | 讲清「离线是加速，不是能力」 |
| 2 | 测试启动失败，日志是连接 MySQL/Redis | 服务未起、密码/db 错 | 先 ping 中间件；确认 database 11、密码 abc123 | 教会看「第一行 Caused by」 |
| 3 | 冒烟脚本健康检查直接退出 | 后端未启动或端口不是 8016 | 启动后端；确认 `BASE` 默认值 | 先 curl `/api/ping` |
| 4 | 冒烟大量断言取到空值 | 未装 `jq`；第 7 节限流未清理 | 安装 jq；重跑脚本自动清 key | 检查脚本依赖 |
| 5 | 流水线构建失败：找不到 `pom.xml` | 仓库是子目录结构，工作目录未设 `server` | 构建步骤工作目录改为 `server` | 强调仓库结构 |
| 6 | 流水线 Node 构建失败 | 云端网络受限、镜像未配置 | 配置镜像或降级为本地构建前端后随制品上传 | 提前准备降级方案 |
| 7 | 流水线测试阶段失败 | 云端无 MySQL/Redis | 提供云效服务连接/自建中间件，或改 `-DskipTests` 并说明 | 口径必须写清 |
| 8 | 主机部署阶段卡住/失败，提示主机组离线 | 主机组未激活、SSH 22 不通、密钥错误 | 云效检查主机组状态；安全组放行 22；重新接入 | 课上用本地部署兜底 |
| 9 | 部署成功但页面 502 | 后端未启动、端口不对、systemd 未起 | `systemctl status`、`journalctl -u campus-activity`、`curl 127.0.0.1:8016/api/ping` | 从后往前查 |
| 10 | 上传图片 404 | `/opt/campus-activity/uploads` 权限/属主不对；Nginx 未配 `/uploads` | 改属主 `campus`；核对 Nginx 配置并 reload | 演示 `ls -ld` 与 `nginx -t` |
| 11 | systemd 环境变量不生效 | `EnvironmentFile` 路径错、文件权限、未 `daemon-reload` | 修正路径；`systemctl daemon-reload` 后重启 | 讲「环境变量不是猜的」 |
| 12 | jar 启动失败：`Port 8016 was already in use` | 旧进程未停 | `lsof -i :8016` → `kill -15`；用 `deploy.sh stop` | 发布前先 status |

### 10.4 常见问答库（13 问，含标准答题要点）

**Q1 为什么用 Redis 缓存分类和热门活动？**
分类与热门榜读多写少，数据库每次查询都要 JOIN/排序；Redis 10 分钟 TTL + 写操作 `@CacheEvict` 可把热点请求挡在数据库前。演示中可用 `redis-cli keys 'campus:cache:*'` 看到缓存 key。取舍：Redis 成为强依赖，故障时缓存接口不可用（见 Q11）。

**Q2 JWT 与 Session 怎么取舍？**
本项目是「小程序 + 后台 + 多端」无状态场景，JWT 自包含身份与角色，服务端不需要 Session 存储，水平扩展简单；代价是登出与禁用账号不能立即全端失效，所以补了 Redis 黑名单（按 `jti` 拉黑）与 2 小时有效期。Session 更适合强会话管理、需要立即踢下线的单体应用。结论：本项目选 JWT + 黑名单，是正确的工程折中。

**Q3 如何防止重复报名、名额不超卖？**
三层保证：服务层先查重给出友好提示；数据库 `uk_activity_user (activity_id,user_id)` 唯一索引兜底并发插入；名额占用用单条条件 UPDATE（`WHERE capacity=0 OR signed_count<capacity`），由影响行数决定成败，InnoDB 行锁保证并发串行。候补转正前重新占位，只有占到才转正。

**Q4 流水线失败怎么定位？**
先看红在哪个阶段：测试（中间件/断言）→ 构建（目录/依赖/网络）→ 制品（路径/文件）→ 部署（主机组/权限/端口）。然后读该阶段日志第一行异常，再回到本机复现同样命令。课堂口诀：**阶段 → 日志 → 本机复现 → 修复 → 重跑**。

**Q5 为什么用 Spring Security 过滤器链，不用原来的拦截器？**
拦截器只能处理进入 Controller 之后的请求，无法统一处理过滤器级异常；Security 提供标准过滤器链、方法级 `@PreAuthorize`、`AuthenticationManager`、BCrypt、统一 401/403 JSON，且能通过 `JwtAuthenticationFilter` 在进入业务前完成鉴权与 `UserContext` 注入。

**Q6 401 和 403 为什么要区分，为什么统一 JSON？**
401 是「你是谁不清楚」（未登录、过期、拉黑），403 是「知道你是谁但没权限」（角色不足）。统一 JSON（`code=10001/10002`）让前端能区分「去登录」还是「提示无权限」，避免前端解析 HTML 错误页。

**Q7 短信验证码如何防刷？**
三条防线：发送间隔 60 秒（`SET NX EX`）、当日上限 10 条（计数器）、连续输错 5 次作废；验证码一次性使用（状态置已用）。生产还要关闭 `expose-code`，否则验证码会随响应泄露。

**Q8 登出为什么要黑名单，不能只清前端 token 吗？**
只清前端，旧 token 在有效期内仍可被复制使用。黑名单把 `jti` 写入 Redis（TTL=剩余有效期），过滤器命中即按匿名处理返回 401，实现真正的服务端失效。代价是 Redis 依赖，故障时降级为放行（已记录风险）。

**Q9 文件上传怎么保证安全？**
顺序校验：空文件 → 大小 ≤10MB → 扩展名白名单（17 种）→ 文件头魔数（拦截可执行文件与伪装图片）→ `bizType` 白名单防目录穿越；本地存储路径 `normalize` 后校验仍在根目录内；上传接口必须登录。生产建议切 OSS 并限制 Bucket 权限。

**Q10 开发用 Vite 代理，生产怎么办？**
开发期 5174/5173 各自代理 `/api`、`/uploads` 到 8016，避免 CORS；生产由 Nginx 同域提供静态页并反代 `/api`、`/uploads` 到 `127.0.0.1:8016`，浏览器始终同源，不需要 CORS。两种环境共用同一套相对路径前端代码。

**Q11 Redis 挂了系统会怎样？**
分类/热门缓存接口 500；短信登录不可用；登出写黑名单失败；黑名单查询降级为「按未拉黑处理」（已登出 token 在剩余有效期内仍可用）；定时任务锁获取失败本轮跳过。这是当前单点 Redis 的已知限制，生产应做主从/哨兵并纳入监控。

**Q12 候补转正如何保证唯一？**
取消报名后先释放名额，取 `status=2` 中 `waitlist_seq` 最小的记录，转正前重新调用占位 UPDATE，只有影响行数 1 才改为 SUCCESS；两个并发取消也只有一个能占到释放的名额，不会双转正。

**Q13 签到码如何防伪造与重放？**
服务端用 HMAC-SHA256(activityId:时间片) 生成 16 位 token，30 秒一片、只接受最近 3 片；不落库、只存密钥；重复签到由 `uk_signup` 唯一索引拦截返回 40003；定位签到用 Haversine 判 200 米范围。
