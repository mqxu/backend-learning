## 5 知识精讲

> 一页一个主题，配表/代码；重点讲“为什么这样设计”，实现细节留给代码走读。

### 5.1 业务全景与两条状态机

一次活动从发布到统计的主线：

```text
组织者建活动(DRAFT) → 提交审核(PENDING) → 团委审核通过(PUBLISHED)
  → 学生报名：需审核→PENDING / 有名额→SUCCESS / 满员→WAITLIST
  → 组织者出签到码 → 学生扫码签到(CHECKED_IN)
  → 活动结束：定时任务把活动置 FINISHED、未签到的 SUCCESS 置 NO_SHOW
```

**活动状态机（7 态）**：草稿 0 → 待审核 1 → 已驳回 2 / 已发布 3 → 进行中 4 → 已结束 5；任意非取消态可 → 已取消 6。学生端只可见 3/4/5。

| 迁移 | 触发 | 实现位置 |
| --- | --- | --- |
| DRAFT→PENDING | 组织者提交审核 | `ActivityService.submit` |
| PENDING→PUBLISHED/REJECTED | 团委审核 | `ActivityService.audit` |
| REJECTED→PENDING | 修改后重新提交 | `ActivityService.submit` |
| PUBLISHED→ONGOING→FINISHED | 定时任务 | `ActivityStatusJob.advanceStatus` |
| PUBLISHED/ONGOING→PENDING | 编辑后自动重审 | `ActivityService.update` |
| 任意非取消→CANCELLED | 组织者取消/管理员下架 | `cancelInternal` |

**报名状态机（7 态）**：待审核 0、报名成功 1、候补中 2、已签到 3、已取消 4、审核未通过 5、未到场 6。占名额的是 `SUCCESS/CHECKED_IN/NO_SHOW`；可取消的是 `PENDING/SUCCESS/WAITLIST`。

> 提问 Q1：为什么“已发布的活动被编辑后要回到待审核”？（防止先发布再改时间地点绕过审核，对应 BR-14。）

### 5.2 JWT 与无状态鉴权

三种登录入口，签发的 token 完全等价：

| 入口 | 接口 | 校验方式 | 说明 |
| --- | --- | --- | --- |
| 微信登录（dev 模式） | `POST /api/app/auth/login` | `devOpenId` 直接作为 openid 查/建号 | 生产用微信 `code` 换 openid |
| 手机号验证码 | `POST /api/app/auth/sms/login` | Redis 中的验证码 | 首次登录自动建号 |
| 后台账号密码 | `POST /api/admin/auth/login` | `AuthenticationManager` + BCrypt | 仅 ADMIN/REVIEWER |

JWT 载荷（HS256，密钥 `campus.jwt.secret`，有效期 `campus.jwt.access-token-hours` 默认 2 小时）：

| 声明 | 含义 |
| --- | --- |
| `sub` | 用户 ID（字符串） |
| `role` | STUDENT / ORGANIZER / REVIEWER / ADMIN |
| `orgId` | 组织 ID，可为空 |
| `nickname` | 昵称 |
| `jti` | 令牌唯一 ID，登出时写入黑名单 |
| `iat` / `exp` | 签发时间、过期时间 |

**为什么无状态**：服务端不保存会话，水平扩容不需要粘性会话；代价是“登出”必须靠黑名单（见 5.6）。**为什么同时写 `UserContext`**：业务代码大量使用 `UserContext.requireUserId()`，因此 `JwtAuthenticationFilter` 在写 `SecurityContext` 的同时写 ThreadLocal，请求结束在 `finally` 清理，避免线程池串号。

> 提问 Q2：token 里为什么不放密码？payload 能被客户端解开吗？（payload 只是 Base64，不是加密。）

### 5.3 Spring Security 链路与角色矩阵

关键类都在 `server/src/main/java/com/campus/activity/`：

| 组件 | 路径 | 职责 |
| --- | --- | --- |
| `SecurityConfig` | `config/SecurityConfig.java` | 过滤器链、路径规则、CORS、`AuthenticationManager`、`BCryptPasswordEncoder` |
| `JwtAuthenticationFilter` | `security/JwtAuthenticationFilter.java` | 解析 Bearer、查黑名单、写双上下文、`finally` 清理 |
| `TokenBlacklistService` | `security/TokenBlacklistService.java` | 黑名单写/查（`campus:auth:blacklist:<jti>`） |
| `SysUserDetailsService` | `security/SysUserDetailsService.java` | 按 username 查 `sys_user`，供后台登录 |
| `JsonAuthenticationEntryPoint` / `JsonAccessDeniedHandler` | `security/` | 401/10001 与 403/10002 固定 JSON |
| `SecurityExceptionAdvice` | `security/SecurityExceptionAdvice.java` | 兜底方法级 `@PreAuthorize` 拒绝 |

请求处理顺序：过滤器解析 JWT 并写双上下文 → 路径级规则（`SecurityFilterChain`）→ 方法级规则（`@PreAuthorize`）→ 业务代码 → `finally` 清理。路径级拒绝走 `ExceptionTranslationFilter`（401 EntryPoint / 403 DeniedHandler）；方法级拒绝由 `SecurityExceptionAdvice` 抢先输出同样 JSON。

| 路径 | 规则 |
| --- | --- |
| `OPTIONS /**`、`/api/ping`、`/api/app/auth/login`、`/api/app/auth/sms/**`、`/api/admin/auth/login`、`/error`、`/uploads/**`、Swagger | `permitAll` |
| `/api/admin/**` | `hasAnyRole("REVIEWER","ADMIN")` |
| `/api/org/**` | `hasAnyRole("ORGANIZER","ADMIN")` |
| `/api/files/**` | `authenticated` |
| 其余 | `permitAll`（登录校验交给方法级） |

| 控制器 | 方法级/类级规则 |
| --- | --- |
| `AppAuthController`、`AppUserController`、`AppCheckinController`、`AppSignupController`、`AppActivityController`、`FileController`、`AdminAuthController` | 方法级 `isAuthenticated()` |
| `AppNoticeController` | 类级 `isAuthenticated()` |
| `OrgController` | 类级 `hasAnyRole('ORGANIZER','ADMIN')` |
| `AdminActivityController`、`AdminDashboardController` | 类级 `hasAnyRole('REVIEWER','ADMIN')` |
| `AdminUserController` | 类级 `hasAnyRole('ADMIN')` |

**为什么需要 `SecurityExceptionAdvice`**：方法级注解在 Controller 调用栈内生效，抛出的 `AccessDeniedException` 会先被 Spring MVC 的 `@RestControllerAdvice` 接住；项目里 `GlobalExceptionHandler` 有 `@ExceptionHandler(Exception.class)` 兜底，不抢在前面处理会把 401/403 转成 500。该 advice 用最高优先级按“匿名→401/10001、已登录→403/10002”复用两个既有处理器，保证与路径级响应体一致。

固定响应体：

```http
HTTP/1.1 401 Unauthorized
{"code":10001,"message":"未登录或登录已过期","data":null}

HTTP/1.1 403 Forbidden
{"code":10002,"message":"没有操作权限","data":null}
```

> 提问 Q3：学生访问 `/api/admin/activities` 返回 401 还是 403？（已登录学生 403；匿名 401。）

### 5.4 Redis 缓存：分类与热门榜

| 场景 | 位置 | 注解 | 失效 |
| --- | --- | --- | --- |
| 分类 | `ActivityService.categories()` | `@Cacheable(cacheNames="categories", key="'all'")` | TTL 10 分钟 |
| 热门活动 | `ActivityService.hot(limit)` | `@Cacheable(cacheNames="activity-hot", key="#limit")` | TTL 10 分钟 + 写操作 `@CacheEvict(allEntries=true)` |
| 写操作失效 | create/update/cancelByOrg/offline/audit | `@CacheEvict(cacheNames="activity-hot", allEntries=true)` | 审核后热门榜不陈旧 |

`config/RedisConfig` 关键实现（为什么这么写）：

| 项 | 值 | 原因 |
| --- | --- | --- |
| 缓存管理器 | 自定义 `RedisCacheManager` | 显式控制 TTL、前缀、序列化，不依赖 Boot 自动配置 |
| key 前缀 | `campus:cache:` + `cacheName::key` | 得到 `campus:cache:categories::all`、`campus:cache:activity-hot::5` |
| 值序列化 | `GenericJacksonJsonRedisSerializer` | JSON 可读，`redis-cli` 可直接看；类型白名单降低反序列化风险 |
| 写入策略 | `immediateWrites()` | Spring Data Redis 4 默认延迟写，演示时“写完立刻读”可能读不到 |
| null 缓存 | 开启 | 防止空结果反复查库 |

`application.yml` 的 `spring.data.redis.*` 只配连接信息；缓存 TTL/前缀/策略只在 `RedisConfig` 中定义（避免两套口径）。

> 提问 Q4：审核通过后为什么要清 `activity-hot`？（热门榜按累计报名数排序，审核/下架会改变可见活动集合。）

### 5.5 短信验证码：Mock 通道与四道防线

链路：`SmsAuthController` → `SmsAuthService` → `SmsCodeService` → `SmsSender`（`MockSmsSender` / `CloopenSmsSender` 条件装配）。

| 防线 | 参数 | 超限错误码 | Redis key |
| --- | --- | --- | --- |
| 手机号格式 | `^1[3-9]\d{9}$` | 60001 | — |
| 发送间隔 | 60 秒（`send-interval-seconds`） | 60002 | `campus:sms:interval:<phone>` |
| 当日上限 | 10 条（`send-daily-limit`） | 60003 | `campus:sms:daily:<phone>` |
| 验证码有效期 | 300 秒（`code-expire-seconds`） | 60004 | `campus:sms:code:<phone>`（Hash：`code`/`status`） |
| 错误次数 | 5 次（`max-fail-count`） | 60006 | `campus:sms:fail:<phone>` |
| 已使用 | `status=1` | 60007 | 同上 code Hash |

重要实现细节：

1. 发送成功后才写验证码 Hash；发送失败会删除冷却 key 允许立即重试；
2. 验证码用 `SecureRandom` 生成 6 位数字并 `%06d` 补零，存字符串，前导 0 不丢；
3. Mock 通道日志格式：`[短信模拟] 向 138****0003 发送验证码：123456`；
4. `campus.sms.expose-code=true` 时响应里带 `mockCode`（仅教学/演示；生产必须改 `false`）；
5. 手机号首次登录自动建号（`open_id=phone:<手机号>`、角色 STUDENT、昵称“手机用户+后 4 位”），`needBind=true` 时仍走绑定接口。

> 提问 Q5：为什么验证码存 Redis Hash 而不是只存一个字符串？（要同时保存“验证码 + 是否已使用”两个状态，且一次登录后置为已使用但保留到过期。）

### 5.6 JWT 黑名单与登出

| 步骤 | 实现 |
| --- | --- |
| 签发 | `JwtUtil.generate` 写入随机 `jti`（`id(UUID)`） |
| 登出 | `POST /api/app/auth/logout`（或 `/api/admin/auth/logout`）→ `AuthService.logout` 解析 `jti` 与 `exp` |
| 写黑名单 | `TokenBlacklistService.block(jti, Duration.between(now, exp))` → `campus:auth:blacklist:<jti>` = `1` |
| 校验 | 后续请求在 `JwtAuthenticationFilter` 查 `isBlocked(jti)`，命中则按匿名处理 → 401 |
| 边界 | token 已过期/格式非法时登出直接返回成功；黑名单 TTL 等于剩余有效期，到期自动删除 |

设计取舍：黑名单粒度为 token，同一账号其他设备的 token 不受影响（不是“全端下线”）；Redis 查询异常时按“未拉黑”降级并记 `warn`，属可用性优先；登出写黑名单异常不捕获，返回 500。

> 提问 Q6：要实现“改密码后所有旧 token 失效”，该怎么做？（按用户维度维护令牌版本/密码修改时间，与 `iat` 比较。）

### 5.7 定时任务与 Redis 分布式锁

| 项 | 内容 |
| --- | --- |
| 触发 | `@Scheduled(cron = "0 */5 * * * ?")`，每 5 分钟 |
| 执行体 | `ActivityStatusJob.advanceStatus()`，`@Transactional` |
| 内容 | PUBLISHED→ONGOING（到开始时间）；PUBLISHED/ONGOING→FINISHED（到结束时间）并把该活动 SUCCESS→NO_SHOW |
| 锁 | `RedisLock.tryLock("campus:lock:activity-status-job", 120)`，`SET NX EX` + 随机 UUID |
| 释放 | `finally` 中 Lua 比对持有者后删除，避免误删别人的锁；进程崩溃 120 秒自动过期 |
| 幂等 | 已推进的活动不再满足查询条件；NO_SHOW 只命中 SUCCESS |

> 提问 Q7：为什么报名名额不用 Redis 锁？（名额由 MySQL 单条条件 UPDATE 保证原子性；Redis 锁只解决“多实例只有一个任务在跑”。）

### 5.8 四个关键算法（为什么这样设计）

**① 名额条件占位（不超卖）**——不做“先查后写”：

```sql
UPDATE activity
   SET signed_count = signed_count + 1
 WHERE id = #{activityId} AND deleted = 0
   AND (capacity = 0 OR signed_count < capacity)
```

调用方只看影响行数：`1` 占位成功；`0` 说明满员 → 开候补进 WAITLIST，否则 30001。并发下由 InnoDB 行锁保证原子性。

**② 候补转正（占位成功才改状态）**——`SignupService.promoteWaitlist`：取队首（`status=2 ORDER BY waitlist_seq, create_time LIMIT 1`）→ 先 `occupySeat`，只有影响行数为 1 才把状态改为 SUCCESS 并发消息；占位失败保持 WAITLIST，避免“已转正但没名额”的脏数据。

**③ 动态签到码（不落库）**——`CheckinTokenService`：`token = activityId.slice.signature`，`signature = HMAC-SHA256(activityId + ":" + slice)` 十六进制前 16 位；`slice = 当前毫秒/1000/30`；校验时从当前片向前遍历 2 片（约容忍 90 秒）。token 与活动天然绑定，客户端无法伪造。

**④ 扫码签到校验顺序（先便宜后昂贵）**——`CheckinService.checkin`：令牌有效(40001) → 活动存在(20001) → 非“仅手动”(40004) → 在签到窗口(40004) → 有报名(40002) → 未签到(40003) → 状态为 SUCCESS(40002) → 定位 ≤200 米(40005，仅 `checkin_type=2`)。先判令牌避免无意义查库，再判状态避免重复写签到。

> 提问 Q8：签到码为什么可以 30 秒轮换、还允许容错 2 片？（防截图转发，同时容忍网络延迟/跨片扫码。）

## 7 完整复现步骤（Step 0–16）

> 前置：后端已启动、MySQL 与 Redis 可用、`data.sql` 已导入。所有命令在项目根目录执行；`BASE` 默认 `http://127.0.0.1:8016/api`。WSL2 与 macOS 的命令相同（时间计算已兼容两平台）。
>
> 建议先打开一个“变量终端”和一个“观察终端”（Redis/测试）。**8 个必须 `code=0` 的节点**：登录 → 绑定 → 建活动 → 提审 → 管理员登录 → 审核 → 报名 → 扫码签到（统计与短信见 Step 10–11）。

### Step 0 建立变量与工具函数

```bash
BASE=http://127.0.0.1:8016/api
login() { curl -s --noproxy '*' -X POST "$BASE/app/auth/login" \
  -H 'Content-Type: application/json' -d "{\"devOpenId\":\"$1\"}" | jq -r '.data.token'; }
plus_minutes() { date -v+"$1"M +"%Y-%m-%d %H:%M:%S" 2>/dev/null || date -d "+$1 minutes" +"%Y-%m-%d %H:%M:%S"; }
```

预期：`login` 返回 `eyJ...`。失败：无输出 → 后端未启动或 dev-mode 未开；`jq` 找不到 → 按 3.3 节安装。

预期（刚导入种子数据时 `needBind=true`、`bound=false`）：

### Step 3 组织者创建活动


✅ 检查点：`AID` 非空；`echo "$CREATE" | jq -r '.code'` 为 0。

## 8 常见错误与排错

| # | 现象 | 常见原因 | 解决办法 | 教师处理建议 |
| --- | --- | --- | --- | --- |
| 1 | 访问受保护接口返回 401/10001 | 没带 token、token 过期（2 小时）、已登出、签名错 | 重新登录拿新 token；确认 `Authorization: Bearer <token>`；登出后用新 token | 让学生先看“401 是谁返回的”（路径级/方法级） |
| 2 | 返回 403/10002 | 角色不足（学生访问 `/api/admin/**`、`/api/org/**`） | 换对应角色 token；不要复用学生 token 调后台 | 用这一步讲清 401/403 分界 |
| 3 | 报名返回 30002 | 同一活动同一用户已有有效报名 | 已取消/审核未通过可重新报名；其余状态属正常拦截 | 引导看 `uk_activity_user` 与状态判断 |
| 4 | 报名返回 30001 | 满员且未开候补 | 让组织者把 `waitlistEnabled` 设为 1 或提高容量 | 结合条件 UPDATE 讲不超卖 |
| 5 | 报名返回 20005 | 活动非 PUBLISHED 或不在报名窗口 | 确认已审核通过；检查 `signupStartTime/signupEndTime` | 强调“演示活动时间要覆盖当前时刻” |
| 6 | 签到返回 40001 | 签到码过期（>约 90 秒）、伪造、活动不匹配 | 重新取码并立即签到 | 用伪造码演示验签失败 |
| 7 | 签到返回 40003/40002 | 已签到 / 未报名或报名未成功 | 40003 属正常幂等拦截；40002 先报名 | 讲“先判状态再写库” |
| 8 | 签到返回 40004 | 不在签到窗口/活动仅手动签到 | 调整活动开始时间或改用组织者补签 | 结合 `checkinType=3` 说明 |
| 9 | 分类/热门接口 500 | Redis 未启动、密码错、`RedisConfig` 未生效 | `redis-cli ... ping`；核对 `spring.data.redis`；看第一个 `Caused by` | 现场演示 Redis 故障降级差异 |
| 10 | 缓存反序列化报错 | 缓存值与当前类型不匹配（改过字段/旧缓存） | 删 `campus:cache:*` 后重试；序列化器类型白名单见 12 文档 4.3 节 | 强调“改 POJO 后清缓存” |
| 11 | 短信 60002/60005/60007 | 60 秒内重复发、码错、码已用 | 清 `campus:sms:*` 对应 key 后重试；注意码只能用一次 | 让学生用 `redis-cli` 查 Hash |
| 12 | `mvn -o test` 全红 | MySQL/Redis 未启动、种子数据被污染、端口冲突 | 停后端 → 重导数据 → 确认中间件 → 再跑 | 测试前统一“恢复种子数据” |

> 排错顺序：**先看 HTTP 状态与 code（谁拒绝）→ 再看 token 角色/有效期 → 再看业务前置条件 → 最后看日志与 Redis**。

## 9 教师引导策略

### 9.1 提问链（≥5，按课堂顺序）

| # | 问题 | 期望回答要点 | 追问 |
| --- | --- | --- | --- |
| Q1 | 已发布的活动被编辑后为什么要回到待审核？ | 防止先发布再改时间地点绕过审核（BR-14） | 学生已报名怎么办？ |

### 9.3 时间控制与“5 分钟原则”

| 规则 | 做法 |
| --- | --- |
| 5 分钟原则 | 同一链路节点卡住超过 5 分钟 → 先跳过该节点继续后续（用教师演示数据），课后定位；不让一个 40001 拖垮全组 |
| 演示不重复 | curl 链路教师只演示一遍，之后用“巡检表 + 组内互助” |
| 检查点硬截止 | 到点收证据（截图/MR 链接），未交课后补交 |
| 代码走读控时 | 20 分钟走读按“10 分钟讲 + 5 分钟学生标记 + 5 分钟答疑”切分，不逐行念代码 |

### 12.1 链路命令速查（完整逐步版见第 7 章）

```bash
BASE=http://127.0.0.1:8016/api
login() { curl -s -X POST "$BASE/app/auth/login" -H 'Content-Type: application/json' \
  -d "{\"devOpenId\":\"$1\"}" | jq -r '.data.token'; }
plus() { date -v+"$1"M +"%Y-%m-%d %H:%M:%S" 2>/dev/null || date -d "+$1 minutes" +"%Y-%m-%d %H:%M:%S"; }
A=$(login mock-student-1); B=$(login mock-student-2); O=$(login mock-organizer-1)
curl -s -X POST "$BASE/app/auth/bind" -H "Authorization: Bearer $A" -H 'Content-Type: application/json' -d '{"studentNo":"2023001","realName":"张小明"}'
curl -s -X POST "$BASE/app/auth/bind" -H "Authorization: Bearer $B" -H 'Content-Type: application/json' -d '{"studentNo":"2023002","realName":"李小红"}'
AID=$(curl -s -X POST "$BASE/org/activities" -H "Authorization: Bearer $O" -H 'Content-Type: application/json' \
  -d "{\"title\":\"课演 $(date +%H%M%S)\",\"categoryId\":1001,\"startTime\":\"$(plus 25)\",\"endTime\":\"$(plus 150)\",\"signupStartTime\":\"$(date '+%Y-%m-%d %H:%M:%S')\",\"signupEndTime\":\"$(plus 20)\",\"locationName\":\"大学生活动中心\",\"capacity\":1,\"waitlistEnabled\":1,\"auditRequired\":0,\"checkinType\":1}" | jq -r '.data.id')
curl -s -X POST "$BASE/org/activities/$AID/submit" -H "Authorization: Bearer $O"
AD=$(curl -s -X POST "$BASE/admin/auth/login" -H 'Content-Type: application/json' -d '{"username":"admin","password":"Admin@123"}' | jq -r '.data.token')
curl -s -X POST "$BASE/admin/activities/$AID/audit" -H "Authorization: Bearer $AD" -H 'Content-Type: application/json' -d '{"pass":true}'
curl -s -X POST "$BASE/app/activities/$AID/signup" -H "Authorization: Bearer $A" -H 'Content-Type: application/json' -d '{}'
curl -s -X POST "$BASE/app/activities/$AID/signup" -H "Authorization: Bearer $B" -H 'Content-Type: application/json' -d '{}'
C=$(curl -s "$BASE/org/activities/$AID/checkin-qr" -H "Authorization: Bearer $O" | jq -r '.data.token')
curl -s -X POST "$BASE/app/checkin" -H "Authorization: Bearer $A" -H 'Content-Type: application/json' -d "{\"token\":\"$C\",\"latitude\":32.11,\"longitude\":118.92}"
SMS=$(curl -s -X POST "$BASE/app/auth/sms/send-code" -H 'Content-Type: application/json' -d '{"phone":"13800000003"}')
SMS_TOKEN=$(curl -s -X POST "$BASE/app/auth/sms/login" -H 'Content-Type: application/json' \
  -d "{\"phone\":\"13800000003\",\"code\":\"$(echo "$SMS" | jq -r '.data.mockCode')\"}" | jq -r '.data.token')
curl -s -X POST "$BASE/app/auth/logout" -H "Authorization: Bearer $SMS_TOKEN"
```
