00先分清三件套

Servlet 规范给容器留了三个可替换的零件。写业务的是 Servlet，改请求的是 Filter，收事件的是 Listener。拦截器不在这份名单里，它属于 Spring MVC，位置在 DispatcherServlet 内部，第 05 节单独讲。

零件规范接口在链路里的位置能做什么
Servlet jakarta.servlet.http.HttpServlet 最内层，真正处理请求 读写响应体。Spring MVC 里由 DispatcherServlet 统一顶替，业务代码写 Controller。
Filter jakarta.servlet.Filter Servlet 之前，可以挂多层 进可改请求、退可改响应，还能直接短路。能拦住静态资源。
Listener jakarta.servlet.*Listener 不属于请求链路，挂在事件上 被动接收应用启动、会话创建、属性变更这类通知，不改请求也不改响应。

04-web 里已经有两个东西在统计耗时：RequestTimeFilter 和 LogInterceptor。同一个请求会打出两条日志，数值还不一样。这不是重复，是两层各记各的：过滤器包住整个 DispatcherServlet，拦截器只包 Controller 那一段，所以过滤器的数值总是更大。

维度FilterHandlerInterceptor
归属Servlet 规范，容器调用Spring MVC，框架调用
能否知道进的是哪个方法不能能，preHandle 有 handler 参数
能否改 request / response能，用包装器整体替换只能读，不能换掉对象
静态资源会经过路径匹配到也会经过，但拿到的是 ResourceHttpRequestHandler
能否依赖注入注册成 Bean 时可以可以
典型用途traceId、编码、跨域、请求体缓存、限流登录校验、日志、权限注解
怎么选

需要换掉 request 或 response、需要覆盖静态资源、或者请求根本到不了 Spring MVC 也要处理，用过滤器。需要知道目标方法、要读注解，用拦截器。两个都要时，过滤器放外层做通用处理，拦截器在里层做业务判断。

02过滤器的链式模型

接口只有一个方法，参数里带着下家的引用：

void doFilter(ServletRequest request, ServletResponse response, FilterChain chain)
        throws IOException, ServletException;

关键在于 chain.doFilter(...) 这一行：它之前是进方向，它之后是出方向。整条链像俄罗斯套娃，容器把第一个过滤器放在最外层。想短路，不调用 chain.doFilter 就行——后面所有过滤器、DispatcherServlet、Controller 都不会执行。

必要条件
每层都要往下传

漏掉 chain.doFilter，请求就停在当前这一层，浏览器那边只会看到一个空响应。

顺序
由 order 决定

数字小的先进入、后返回。没写 order 的默认排在最外层之外的最后，容易被 Tomcat 自带的过滤器挤到奇怪的位置。

过滤器里抛异常，谁接

@RestControllerAdvice 挂在 DispatcherServlet 内部，过滤器在它外面，异常传不进去。容器会转发到 /error，返回的是 Spring Boot 的默认错误结构，不是项目里的 Result。所以过滤器里要么自己 try-catch 写响应，要么统一用 ErrorController 兜底。

03三种注册方式

同一个 Filter 有三种挂到容器上的写法，差别在顺序、路径、依赖注入这三点。

方式顺序控制路径控制能否注入 Bean适用
@Component + @Order @Order 注解 默认 /*，无法指定 能 全局通用处理
FilterRegistrationBean setOrder addUrlPatterns 能 要限路径、要能关掉
@WebFilter + @ServletComponentScan 不能，靠注册先后 urlPatterns 不能，实例由容器 new 老项目迁移、示例

第一种最省事，类上加两个注解就是一层过滤器：

@Slf4j
@Component
@Order(Ordered.HIGHEST_PRECEDENCE)
public class TraceIdFilter extends OncePerRequestFilter {

    public static final String TRACE_ID = "traceId";

    @Override
    protected void doFilterInternal(HttpServletRequest request, HttpServletResponse response,
                                    FilterChain chain) throws ServletException, IOException {
        String traceId = request.getHeader("X-Trace-Id");
        if (traceId == null || traceId.isBlank()) {
            traceId = UUID.randomUUID().toString().replace("-", "").substring(0, 16);
        }
        MDC.put(TRACE_ID, traceId);
        response.setHeader("X-Trace-Id", traceId);
        try {
            chain.doFilter(request, response);
        } finally {
            MDC.remove(TRACE_ID);
        }
    }
}

第二种把注册信息写成 Bean，顺序、路径、开关都在代码里显式写出来。项目里 ParameterCleanFilter 和 ApiKeyFilter 都是这个路子：

@Configuration
public class FilterConfig {

    @Bean
    public FilterRegistrationBean<ApiKeyFilter> apiKeyFilter() {
        FilterRegistrationBean<ApiKeyFilter> bean =
                new FilterRegistrationBean<>(new ApiKeyFilter());
        bean.setName("apiKeyFilter");
        bean.addUrlPatterns("/demo/secure");
        bean.setOrder(Ordered.HIGHEST_PRECEDENCE + 30);
        return bean;
    }
}

第三种靠启动类上的扫描注解把 @WebFilter 找出来。Spring Boot 4 的包路径变了，从 org.springframework.boot.web.servlet 挪到了 org.springframework.boot.web.server.servlet.context，照旧路径写会直接编译不过：

@SpringBootApplication
@ServletComponentScan   // org.springframework.boot.web.server.servlet.context.ServletComponentScan
public class WebApplication {
    public static void main(String[] args) {
        SpringApplication.run(WebApplication.class, args);
    }
}
@Slf4j
@WebFilter(urlPatterns = "/demo/annotation/*", filterName = "annotationDemoFilter")
public class AnnotationDemoFilter implements Filter {

    @Override
    public void doFilter(ServletRequest request, ServletResponse response, FilterChain chain)
            throws IOException, ServletException {
        HttpServletRequest httpRequest = (HttpServletRequest) request;
        log.info("@WebFilter 生效：{} {}", httpRequest.getMethod(), httpRequest.getRequestURI());
        chain.doFilter(request, response);
    }
}
两个容易出事的地方

@WebFilter 的实例是 Tomcat 创建的，不是 Spring Bean，里面写的 @Autowired 字段会是 null，运行时才炸。要注入依赖就换成前两种写法。

一个 Filter 类如果既是 @Component 又在 FilterConfig 里注册了一次，Boot 只会注册一次，但顺序按 FilterRegistrationBean 的来，@Order 就失效了。改顺序时先确认自己改的是哪一处。

04用包装器改请求

过滤器能改请求，靠的不是修改原对象，而是把 HttpServletRequestWrapper 包一层再传给下一层。Wrapper 默认把所有方法原样转发，只覆盖需要改的那几个。

项目里的 ParameterCleanFilter 做的事很具体：参数两端带空格时，Controller 收到的就是去掉空格的值。

public class ParameterCleanFilter extends OncePerRequestFilter {

    @Override
    protected void doFilterInternal(HttpServletRequest request, HttpServletResponse response,
                                    FilterChain chain) throws ServletException, IOException {
        chain.doFilter(new TrimmedRequest(request), response);
    }

    static final class TrimmedRequest extends HttpServletRequestWrapper {

        private final Map<String, String[]> values;

        TrimmedRequest(HttpServletRequest request) {
            super(request);
            Map<String, String[]> copy = new LinkedHashMap<>();
            request.getParameterMap().forEach((name, origin) -> copy.put(name, trimAll(origin)));
            this.values = Collections.unmodifiableMap(copy);
        }

        private static String[] trimAll(String[] origin) {
            return Arrays.stream(origin).map(v -> v == null ? null : v.trim()).toArray(String[]::new);
        }

        @Override
        public String getParameter(String name) {
            String[] value = values.get(name);
            return value == null || value.length == 0 ? null : value[0];
        }

        @Override
        public String[] getParameterValues(String name) {
            return values.get(name);
        }

        @Override
        public Map<String, String[]> getParameterMap() {
            return values;
        }
    }
}

实测：请求 /demo/trim?name=%20%20abc%20%20，Controller 拿到的长度是 3。

{"code":200,"data":"收到参数长度 3，值 [abc]","message":"success"}
包装请求的代价

getParameterMap() 会强制容器解析请求体。表单上传（multipart/form-data）时这等于提前把文件流读完，后面 MultipartResolver 就拿不到内容了。真实项目里用 shouldNotFilter 把上传路径排掉。

想要缓存 body 以便多次读取，别自己接 getInputStream，直接用 ContentCachingRequestWrapper，或者 Boot 自带的 ContentCachingFilter。

@Override
protected void doFilterInternal(HttpServletRequest request, HttpServletResponse response,
                                FilterChain chain) throws ServletException, IOException {
    ContentCachingRequestWrapper wrapper = new ContentCachingRequestWrapper(request);
    chain.doFilter(wrapper, response);
    // 请求结束之后才有完整内容
    log.info("请求体：{}", new String(wrapper.getContentAsByteArray(), StandardCharsets.UTF_8));
}

05拦截器的三个回调

过滤器决定请求能不能进，拦截器决定进来之后怎么处理。Spring MVC 在 DispatcherServlet 内部给拦截器留了四个回调，常用的三个。

项目里 LogInterceptor 是最小例子：preHandle 把开始时间塞进 request，afterCompletion 拿出来算差值。要看三个回调的实际调用顺序，再挂一个只打日志的：

@Slf4j
@Component
public class CallbackTraceInterceptor implements HandlerInterceptor {

    @Override
    public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler) {
        log.info("preHandle：{} {}，handler = {}", request.getMethod(), request.getRequestURI(),
                handler.getClass().getSimpleName());
        return true;
    }

    @Override
    public void postHandle(HttpServletRequest request, HttpServletResponse response, Object handler,
                           ModelAndView modelAndView) {
        log.info("postHandle：{} {}，此时响应还没写出去", request.getMethod(), request.getRequestURI());
    }

    @Override
    public void afterCompletion(HttpServletRequest request, HttpServletResponse response, Object handler,
                                Exception ex) {
        log.info("afterCompletion：{} {}，异常 = {}", request.getMethod(), request.getRequestURI(),
                ex == null ? "无" : ex.getClass().getSimpleName());
    }
}
回调时机要留意的地方
preHandle Controller 执行之前 返回 false 就到此为止，后续拦截器、Controller、postHandle 全部不执行。响应要自己写，状态码也要自己设。
postHandle Controller 执行之后，响应写出之前 Controller 抛异常时不执行。REST 接口这里拿不到返回对象，想改响应体得用 ResponseBodyAdvice，改响应头倒是可以。
afterCompletion 响应完成之后 一定执行（只要进了 preHandle），适合清理 ThreadLocal、打印耗时。异常被 @ExceptionHandler 消化掉之后，这里的 ex 是 null。
afterConcurrentHandlingStarted 异步请求的第一次派发结束时 只在 Controller 返回 Callable、DeferredResult 时触发，用来替代这一次的 postHandle 与 afterCompletion。

Controller 抛异常时，postHandle 直接消失，而 afterCompletion 里的异常是“无”——因为 @RestControllerAdvice 已经把异常处理成了 Result，DispatcherServlet 认为这次请求有结果，回调时传的就是 null：

拦截器返回 false 时，排在它前面的拦截器照样会收到 afterCompletion，它自己的两个回调都不会执行。这也是为什么 LogInterceptor 在 401 的请求上还能打出耗时：

INFO  CallbackTraceInterceptor [87ef92b2a8314478] - preHandle：GET /demo/token/data，handler = HandlerMethod
WARN  TokenInterceptor [87ef92b2a8314478] - TokenInterceptor 拦住请求：GET /demo/token/data，X-Token 不合法
INFO  CallbackTraceInterceptor [87ef92b2a8314478] - afterCompletion：GET /demo/token/data，异常 = 无
INFO  LogInterceptor [87ef92b2a8314478] - 拦截器统计：GET /demo/token/data 耗时 0ms

异步接口最值得看：一次请求，两套回调，两条线程。第一次派发只到 preHandle，过滤器当场结算耗时；异步线程完成后重新派发，才有 postHandle 和 afterCompletion。注意第二段日志的 traceId 是空的：

08:20:46:196 [http-nio-18004-exec-5] INFO  CallbackTraceInterceptor [867188fef110498b] - preHandle：GET /demo/async，handler = HandlerMethod
08:20:46:199 [http-nio-18004-exec-5] INFO  RequestTimeFilter [867188fef110498b] - 过滤器统计：GET /demo/async 耗时 4ms
08:20:46:329 [http-nio-18004-exec-6] INFO  CallbackTraceInterceptor [] - preHandle：GET /demo/async，handler = HandlerMethod
08:20:46:332 [http-nio-18004-exec-6] INFO  CallbackTraceInterceptor [] - postHandle：GET /demo/async，此时响应还没写出去
08:20:46:332 [http-nio-18004-exec-6] INFO  CallbackTraceInterceptor [] - afterCompletion：GET /demo/async，异常 = 无
异步请求里 traceId 去哪了

异步完成后的那次派发是 ASYNC 类型，过滤器不会重跑：OncePerRequestFilter 默认跳过 ASYNC 与 ERROR 派发，普通 Filter 注册时又只映射 REQUEST。所以第二段日志的 MDC 是空的。要让异步线程也带上，就把 traceId 一起传进任务，或用 TaskDecorator 复制 MDC。

注册与排序

拦截器靠 WebMvcConfigurer#addInterceptors 注册，路径与顺序都在这里定。order 小的先执行 preHandle，后执行 postHandle 和 afterCompletion。

@Override
public void addInterceptors(InterceptorRegistry registry) {
    registry.addInterceptor(logInterceptor).addPathPatterns("/**").order(0);
    registry.addInterceptor(callbackTraceInterceptor).addPathPatterns("/demo/**").order(1);
    registry.addInterceptor(tokenInterceptor)
            .addPathPatterns("/demo/token/**")
            .excludePathPatterns("/demo/token/public")
            .order(2);
}

令牌校验写成拦截器也就是一个 preHandle。注意返回 false 之前把响应写完整，否则浏览器会拿到一个没有任何内容的 401：

@Override
public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler)
        throws Exception {
    String token = request.getHeader("X-Token");
    if ("demo-token".equals(token)) {
        return true;
    }
    log.warn("TokenInterceptor 拦住请求：{} {}", request.getMethod(), request.getRequestURI());
    response.setStatus(HttpServletResponse.SC_UNAUTHORIZED);
    response.setContentType("application/json;charset=UTF-8");
    response.getOutputStream().write(
            "{\"code\":401,\"message\":\"缺少或错误的 X-Token\",\"data\":null}".getBytes(StandardCharsets.UTF_8));
    return false;
}
和过滤器怎么分工

项目里 ApiKeyFilter 挡的是“这个服务不该被调用”，TokenInterceptor 挡的是“这个用户没有资格”，两者位置不同、拿到的东西也不同。过滤器只认 path，拦截器还能从 handler 上读注解，做注解式权限判断要放在拦截器里。

06监听器管的是事件

监听器不参与请求处理，它只等容器发通知。所以判断用不用监听器，看的是“有没有一件事发生了”，而不是“要不要拦一个请求”。

MIN+30ApiKeyFilter鉴权放在清洗之后，失败时已有 traceId 便于排查

监听器这边只需要两个类。应用级的最简单：

@Slf4j
@Component
public class AppLifecycleListener implements ServletContextListener {

    @Override
    public void contextInitialized(ServletContextEvent event) {
        log.info("应用启动：contextInitialized，容器 {}", event.getServletContext().getServerInfo());
    }

    @Override
    public void contextDestroyed(ServletContextEvent event) {
        log.info("应用关闭：contextDestroyed，开始释放资源");
    }
}

会话级的稍微复杂一点，一个类可以同时实现多个监听接口，容器按事件类型分派：

@Slf4j
@Component
public class OnlineCountListener implements HttpSessionListener, HttpSessionAttributeListener {

    private final AtomicInteger online = new AtomicInteger();

    public int getOnline() {
        return online.get();
    }

    @Override
    public void sessionCreated(HttpSessionEvent event) {
        log.info("会话创建：{}，当前在线 {}", event.getSession().getId(), online.incrementAndGet());
    }

    @Override
    public void sessionDestroyed(HttpSessionEvent event) {
        log.info("会话销毁：{}，当前在线 {}", event.getSession().getId(), online.decrementAndGet());
    }

    @Override
    public void attributeAdded(HttpSessionBindingEvent event) {
        log.info("会话属性新增：{} = {}", event.getName(), event.getValue());
    }

    @Override
    public void attributeReplaced(HttpSessionBindingEvent event) {
        log.info("会话属性替换：{}，旧值 {}", event.getName(), event.getValue());
    }

    @Override
    public void attributeRemoved(HttpSessionBindingEvent event) {
        log.info("会话属性移除：{}，原值 {}", event.getName(), event.getValue());
    }
}

这个监听器注册成 Bean，所以 DemoController 可以直接注入它，把在线人数当普通对象读出来：

@RestController
@RequestMapping("/demo")
@RequiredArgsConstructor
public class DemoController {

    private final OnlineCountListener onlineCountListener;

    @GetMapping("/online")
    public Result<Integer> online() {
        return Result.ok(onlineCountListener.getOnline());
    }

    @DeleteMapping("/session")
    public Result<String> destroySession(HttpSession session) {
        session.invalidate();
        return Result.ok("会话已销毁");
    }
}

09容易踩的地方

现象原因处理
过滤器完全不执行@WebFilter 类没被扫描启动类加 @ServletComponentScan，注意 Boot 4 的新包路径
顺序和预想相反@Order 写了相同值，或用的是 @WebFilter改用 FilterRegistrationBean.setOrder，并确认没重复注册
过滤器里 @Autowired 拿到 null实例由 Tomcat 创建，不在 Spring 容器里改成 @Component 或注册 Bean
Controller 读到的 body 是空的过滤器已经把输入流读完了，流不能重读用 ContentCachingRequestWrapper
过滤器里改的响应头没出现在浏览器响应已提交（commit），头已经发出去了放在 chain.doFilter 之前设置
异步请求要过滤器再跑一次，或者抱怨它跑了两次派发类型与过滤器基类不匹配：OncePerRequestFilter 默认跳过 ASYNC，普通 Filter 注册时只映射 REQUEST需要就覆盖 shouldNotFilterAsyncDispatch，或在注册时 setDispatcherTypes 指明
拦截器改了响应体没有效果postHandle 拿不到 Controller 的返回对象，REST 场景也没视图可改改响应头放 postHandle，改 body 用 ResponseBodyAdvice
afterCompletion 收不到异常异常已被 @ExceptionHandler 处理，DispatcherServlet 回调时传 null要记录异常就在异常处理器里记，不要指望这个参数
拦截器返回 false 后浏览器收到空响应没有自己写状态码与响应体在 preHandle 里 setStatus 并写 output
异步请求里 MDC 的 traceId 是空的过滤器默认只处理 REQUEST 派发，ASYNC 派发不再进链用 TaskDecorator 复制 MDC，或手动传 traceId
在线人数一直是 0没有真的创建会话，或方案本身无状态检查有没有调用 getSession()；JWT 方案另想办法统计
启动直接失败监听器里抛了异常，容器启动中断启动期逻辑包 try-catch，失败只记日志不抛
静态资源也被拦了过滤器默认覆盖所有路径，拦截器配了 /** 也一样会执行过滤器收窄 addUrlPatterns，拦截器用 excludePathPatterns
排查顺序

先看日志里到底有没有过滤器的输出，判断是没注册还是没执行；再确认路径和 order；最后才怀疑代码逻辑。三步能解决上面九成的问题。

10小测验

点选项即时判分，选完会给出解释。

01同一个请求里，过滤器和拦截器哪个先执行？

过滤器属于 Servlet 规范，在 DispatcherServlet 之前执行；拦截器由 Spring MVC 调用，此时请求已经进到 DispatcherServlet 内部。两者各有一套排序方式。

02写了 @WebFilter 的类完全没生效，最可能的原因是什么？

注解过滤器靠 Servlet 组件扫描发现。Spring Boot 4 里该注解在 org.springframework.boot.web.server.servlet.context 包下，用错包路径同样不生效。

03一个 @Component 的过滤器只想拦 /api/**，最合适的做法是？

路径控制是注册阶段的事。第二种写法虽然能跑，但过滤器照样进链、照样占顺序，还会漏掉 URL 解码等细节，属于把配置问题写进业务代码。

04过滤器里读了一次 request body，Controller 里再读就是空的，怎么办？

Servlet 的输入流只能顺序读一次，读完就到底了。包装器在第一次读的时候把字节缓存起来，后续可以重复获取。顺序无关，除非不读。

05HttpSessionListener.sessionCreated 什么时候触发？

会话是按需创建的。没调用 getSession() 的接口不会建会话；JWT 这类无状态方案不建会话，所以监听器不会触发。

06某个拦截器的 preHandle 返回 false，还有哪些回调会执行？

DispatcherServlet 只对 preHandle 已经返回 true 的拦截器调用 afterCompletion，且传入的异常是 null。这个拦截器自己的 postHandle 与 afterCompletion 都不会执行，Controller 也不会执行。

07Controller 抛出的异常被 @RestControllerAdvice 处理成 Result 之后，拦截器 afterCompletion 收到的 ex 是什么？

DispatcherServlet 先交给 HandlerExceptionResolver 处理，处理成功后再回调 afterCompletion 时传 null。异常没被处理掉才会把这个异常透传过来。

11练习与小结

1
把 traceId 传到底

现在 traceId 只写进 MDC，试着让它进入异步线程（@Async 或线程池提交的任务），验证日志里子线程也带同一个 traceId。

2
给过滤器加开关

在 FilterRegistrationBean 上接一个配置项 demo.filter.api-key.enabled，用 setEnabled 控制，改配置不用改代码。

3
把在线人数换成会话审计

用 HttpSessionAttributeListener 记录“谁在什么时候登录、什么时候退出”，写进一个内存队列，再加一个接口读出来。

4
验证短路的边界

在 ApiKeyFilter 里抛一个运行时异常，观察返回体是不是项目里的 Result，再决定怎么补兜底。

5
换一种权限判断

自定义一个 @RequireRole 注解，在 TokenInterceptor 里从 handler 拿到 HandlerMethod 再读注解。这件事过滤器做不到，因为它拿不到目标方法。

这一节要记住的五句

过滤器在 DispatcherServlet 外面，所以能改请求、能短路、拦得住静态资源，也兜不住全局异常。

链式模型的全部秘密就是 chain.doFilter 这一行分成进出两段，不调用它就是短路。

拦截器的三个回调一进两出：preHandle 正序，postHandle 与 afterCompletion 逆序，抛异常时少了 postHandle。

注册方式决定顺序和路径，注解写法和注册 Bean 不要混着用来控顺序。

监听器是事件通知，不是拦截器；会话事件只在真的建了会话时才有。
