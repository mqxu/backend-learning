# 04 核心业务实现

## 一、登录

### 小程序登录

前端 `uni.login` 拿到 `code`，后端调微信 `jscode2session` 换 `openid`，再按 `openid` 查用户，没有就建一个。

开发阶段不想依赖真实小程序，用 `dev-mode` 跳过微信请求：

```yaml
campus:
  dev-mode: true
```

此时请求体直接传 `devOpenId`：

```bash
curl -X POST http://127.0.0.1:8080/api/app/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"devOpenId":"mock-student-1"}'
```

返回：

```json
{
  "code": 0,
  "data": {
    "token": "eyJ...",
    "needBind": true,
    "user": { "id": 3, "nickname": "张小明", "role": "STUDENT", "bound": false }
  }
}
```

`needBind` 为 true 时前端跳绑定页。`dev-mode` 关闭后才走真实链路，逻辑在 `AuthService.resolveOpenId`，两条分支只差 openid 的来源，后面的建号逻辑共用。

### 学号绑定

绑定要过三道校验：学号在白名单里、学号没有被别人绑过、姓名与白名单一致（姓名以白名单为准，不允许自己改）。

```java
StudentWhitelist whitelist = whitelistMapper.selectOne(...studentNo);
if (whitelist == null) throw new BizException(ResultCode.STUDENT_NO_NOT_FOUND);

StudentProfile exist = profileMapper.selectOne(...studentNo);
if (exist != null && !exist.getUserId().equals(userId)) {
    throw new BizException(ResultCode.STUDENT_NO_BOUND);
}
```

学院、年级、专业允许用户填，留空时取白名单的值。绑定成功后把白名单的 `used_flag` 置 1。

### 后台登录

后台账号也放在 `sys_user`，用 `username` + BCrypt 密码。种子数据里的密码是 `admin` / `Admin@123`，哈希用 `htpasswd -bnBC 10 "" 'Admin@123'` 生成。

`AuthService.adminLogin` 校验后限制角色必须是 `ADMIN` 或 `REVIEWER`，组织者账号不能进后台。

## 二、活动发布与审核

### 创建

创建时状态是草稿，`creator_id` 取当前登录用户，`org_id` 取当前用户所属组织。没有绑定组织的账号直接拒绝：

```java
if (user.orgId() == null) {
    throw new BizException(ResultCode.FORBIDDEN, "当前账号未绑定组织，无法发布活动");
}
```

审批通过后学生才看得到。

### 时间校验

五个时间字段的关系在 `applyRequest` 里一次性校验，任何一条不满足都返回 `20004`：

- 活动开始早于活动结束
- 报名开始不晚于报名结束
- 报名结束不晚于活动开始
- 取消截止不晚于活动开始

`cancel_deadline` 不填时默认活动开始前 2 小时。

### 提交与审核

草稿或已驳回的活动可以提交，状态变 `PENDING`。

审核接口只处理 `PENDING` 状态：

```java
if (activity.getStatus() != ActivityStatus.PENDING.getCode()) {
    throw new BizException(ResultCode.ACTIVITY_STATUS_INVALID, "该活动不在待审核状态");
}
```

通过变 `PUBLISHED` 并写 `publish_time`，驳回变 `REJECTED` 并记 `reject_reason`。每次操作写一条 `audit_record`，记录操作人、前后状态、理由。

### 已发布活动的修改

已发布或被驳回后重新提交的活动，只要改动就退回 `PENDING` 重新审核：

```java
if (activity.getStatus() == ActivityStatus.PUBLISHED.getCode()
        || activity.getStatus() == ActivityStatus.ONGOING.getCode()) {
    activity.setStatus(ActivityStatus.PENDING.getCode());
}
```

这一条防的是先发布一个合规活动、再改成违规内容绕过审核。

## 三、报名

### 状态判定

提交报名的状态由三个条件决定，顺序不能换：

```java
SignupStatus target;
if (activity.needAudit()) {
    target = SignupStatus.PENDING;                 // 需要审核：先待审核，不占名额
} else if (activityMapper.occupySeat(activityId) == 1) {
    target = SignupStatus.SUCCESS;                 // 有位置：占位成功
} else if (activity.waitlistOn()) {
    target = SignupStatus.WAITLIST;                // 满了但有候补：进队
} else {
    throw new BizException(ResultCode.SIGNUP_FULL);
}
```

`occupySeat` 是一条带条件的 UPDATE，见 `02-数据库设计.md`。它的返回值就是并发结果，不需要额外加锁。

### 报名前置条件

按顺序检查，任何一条不满足直接返回：

1. 已绑定学号（`NEED_BIND`）
2. 活动状态是已发布（`ACTIVITY_NOT_OPEN`）
3. 当前时间在报名时间窗内
4. 没有有效报名记录（`SIGNUP_REPEATED`）

第 4 条对已取消、已驳回的记录放行，重新报名时复用同一行数据。

### 候补转正

有人取消报名时，如果原状态占名额，先释放名额，再从候补队列取队首：

```java
ActivitySignup next = signupMapper.findFirstWaitlist(activityId);
if (next == null) return;
if (activityMapper.occupySeat(activityId) != 1) return;   // 名额被别人抢走，放弃本次转正
next.setStatus(SignupStatus.SUCCESS.getCode());
```

占位失败就放弃，不重试。下一轮有人取消时还会再触发。

### 组织者审核报名

活动开启「报名需要审核」时，报名记录是 `PENDING`，组织者通过后才占名额。批量通过时逐个占位，中途名额不足直接抛错回滚整批，避免出现「通过了一半」。

## 四、签到码

签到码不落库，用 HMAC 现算：

```java
long slice = System.currentTimeMillis() / 1000 / sliceSeconds;   // 30 秒一个时间片
String token = activityId + "." + slice + "." + sign(activityId, slice);
```

`sign` 是 `HMAC-SHA256(secret, activityId + ":" + slice)` 取前 16 位十六进制。

校验时接受最近 `toleranceSlices` 个时间片（默认 2 个，即 60 秒）：

```java
long now = currentSlice();
for (int i = 0; i <= toleranceSlices; i++) {
    long candidate = now - i;
    if (candidate == slice && sign(activityId, candidate).equals(parts[2])) {
        return activityId;
    }
}
throw new BizException(ResultCode.CHECKIN_TOKEN_INVALID);
```

这样做的效果：

- 截图转发出去，最多在 60 秒内可用，过期失效
- 服务端不需要存储，也不用清理
- 改 token 里的活动 ID 会导致签名对不上

实现在 `service/CheckinTokenService`。

## 五、签到

学生提交 token 后依次校验：

1. 签名有效（`40001`）
2. 活动存在
3. 活动不是「仅手动签到」模式
4. 当前时间在签到窗口内（活动开始前 30 分钟到结束后 30 分钟，`40004`）
5. 有报名记录（`40002`）
6. 报名状态是报名成功（`40002`），未签到过（`40003`）
7. 定位签到模式下，与场地距离不超过 200 米（`40005`）

通过后写 `activity_checkin`，并把报名状态改成已签到。`uk_signup` 唯一索引保证一个报名只能签到一次，重复提交会触发 `DuplicateKeyException`，转换成 `40003`。

距离用 Haversine 公式算，见 `CheckinService.distanceMeters`。

### 手动补签

组织者在名单页对某条报名补签，必须填原因。补签写 `checkin_type=3`，同时写一条 `audit_record`（`action=MANUAL_CHECKIN`），事后可查。

## 六、定时任务

`job/ActivityStatusJob` 每 5 分钟执行一次：

- 已发布且到开始时间 → 进行中
- 已发布或进行中且到结束时间 → 已结束
- 活动结束时，把该活动下「报名成功」的记录批量改成「未到场」

```java
@Scheduled(cron = "0 */5 * * * ?")
@Transactional
public void advanceStatus() { ... }
```

状态推进慢 5 分钟不会影响正确性：详情接口读取时会按当前时间再算一次按钮文案，列表的「报名中」状态也是实时计算的。

## 七、消息

消息先落 `sys_notice`，再调用 `NoticeSender.sendWechatSubscribeMessage` 发订阅消息。V1 的这个方法只打日志，接入真实模板时改这一处即可，业务代码不用动。

触发点：

| 时机 | 类型 | 接收人 |
| --- | --- | --- |
| 报名成功 / 待审核 / 进候补 | SIGNUP、WAITLIST | 学生 |
| 报名审核通过 / 驳回 | AUDIT | 学生 |
| 候补转正 | WAITLIST | 学生 |
| 取消报名 | SIGNUP | 学生 |
| 活动取消 | CANCEL | 已报名学生（V1 只落库，未批量推送） |
