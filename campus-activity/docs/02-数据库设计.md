# 02 数据库设计

## 表清单

| 表 | 职责 | 关键约束 |
| --- | --- | --- |
| `sys_user` | 学生、组织者、后台账号统一存这里，用 `role` 区分 | `uk_open_id`、`uk_username` |
| `student_profile` | 学号、姓名、学院、年级、专业 | `uk_student_no` |
| `student_whitelist` | 学籍白名单，绑定时的校验依据 | `uk_student_no` |
| `organization` | 社团、院系、部门 | — |
| `org_member` | 组织成员与负责人 | `uk_org_user` |
| `activity_category` | 活动分类 | `uk_code` |
| `activity` | 活动主表 | `idx_status_start` |
| `activity_signup` | 报名记录 | `uk_activity_user`、`uk_signup_no` |
| `activity_checkin` | 签到记录 | `uk_signup` |
| `activity_favorite` | 收藏 | `uk_activity_user` |
| `sys_notice` | 站内消息 | `idx_user_read` |
| `audit_record` | 审核与敏感操作留痕 | `idx_biz` |

主键统一用雪花 ID（`BIGINT`，应用层生成），不使用自增。原因是后续做数据合并或迁移时自增 ID 容易冲突，而 MyBatis-Plus 默认的 `ASSIGN_ID` 已经能处理。

## 状态定义

### 活动 `activity.status`

| 值 | 状态 | 说明 |
| --- | --- | --- |
| 0 | 草稿 | 仅创建人可见 |
| 1 | 待审核 | 学生端不可见 |
| 2 | 已驳回 | 展示驳回理由，可修改重提 |
| 3 | 已发布 | 学生端可见，报名受时间窗控制 |
| 4 | 进行中 | 到开始时间自动切换 |
| 5 | 已结束 | 到结束时间自动切换，未签到标记为未到场 |
| 6 | 已取消 | 组织者或管理员取消 |

### 报名 `activity_signup.status`

| 值 | 状态 | 是否占名额 |
| --- | --- | --- |
| 0 | 待审核 | 否 |
| 1 | 报名成功 | 是 |
| 2 | 候补中 | 否 |
| 3 | 已签到 | 是 |
| 4 | 已取消 | 否 |
| 5 | 审核未通过 | 否 |
| 6 | 未到场 | 是 |

占名额的判定放在 `SignupStatus.occupiesSeat()` 里，业务代码统一调用，避免各处写 `status == 1 || status == 3`。

## 两个关键设计

### 名额占用用条件更新

报名和签到并发时最怕超卖。这里的做法是不查再写，直接一条 UPDATE 让数据库判断：

```sql
UPDATE activity
   SET signed_count = signed_count + 1
 WHERE id = #{activityId}
   AND deleted = 0
   AND (capacity = 0 OR signed_count < capacity)
```

影响行数为 1 表示占位成功，为 0 表示已满。`capacity = 0` 表示不限人数。这条语句在 `ActivityMapper.occupySeat` 中。

事务里再写报名记录。如果报名记录插入失败，事务回滚，占位也一起回滚。

### 唯一索引兜底重复提交

`activity_signup` 上的 `uk_activity_user(activity_id, user_id)` 保证一个用户对一个活动只有一条记录。

用户取消后重新报名时，**复用同一行**（把状态改回成功、清空取消时间），而不是删了再插。这样逻辑删除和唯一索引不会打架。

应用层捕获 `DuplicateKeyException` 后转换成「你已报名该活动」的提示，见 `SignupService.signup`。

## 时间字段

活动有五个时间：

| 字段 | 含义 | 约束 |
| --- | --- | --- |
| `signup_start_time` | 报名开始 | 可以早于当前时间 |
| `signup_end_time` | 报名结束 | 必须早于或等于活动开始 |
| `start_time` | 活动开始 | 必须早于结束 |
| `end_time` | 活动结束 | |
| `cancel_deadline` | 取消报名截止 | 不填时默认活动开始前 2 小时 |

校验写在 `ActivityService.applyRequest`，违反任一条返回 `20004 时间设置不合理`。

## 演示数据

`db/data.sql` 包含 6 个分类、3 个组织、5 个学生、4 场活动，时间是执行时用 `NOW()` 算出来的相对时间，所以随时执行都能得到「可报名 / 待审核」的可用数据。

后端在 `dev-mode=true` 时会检查示例活动是否全部过期，过期就整体平移到未来，避免隔天打开全是「已结束」。相关代码在 `config/DevDataInitializer`。

重置数据：

```bash
cd server/src/main/resources/db
mysql -h127.0.0.1 -P3308 -uroot -p'Campus@2026' campus_activity < schema.sql
mysql -h127.0.0.1 -P3308 -uroot -p'Campus@2026' campus_activity < data.sql
```

`schema.sql` 会先 `DROP TABLE`，执行前确认连的是开发库。
