01项目概述

1.1 背景

校园活动目前依赖海报、班级群、公众号推文分散触达，报名用问卷或群接龙，签到用纸质表格。三个环节各自断点：学生找不到活动，组织者收不齐名单，团委拿不到全校活动数据。活动结束后的参与证明、素质拓展学分认定也无从查证。

1.2 产品目标

覆盖
≥ 80%
试运行一学期，校级与院级活动线上化比例
转化
≥ 70%
报名到实际签到的到场率，用于倒逼活动质量
效率
≤ 5 min
组织者从新建到提交审核完成一次活动发布
  • 学生端：一次搜索或分类浏览即可完成发现、报名、签到、查看记录，不再依赖群消息。
  • 组织者端：在线发布、名单实时可见、扫码核销、活动结束自动出统计。
  • 管理端：活动审核留痕，全校活动数据可按学院、时间、类型聚合。

1.3 范围

范围内容
V1 包含微信登录与学号绑定、活动发布与审核、活动浏览搜索、报名与候补、扫码签到、收藏与消息通知、组织者工作台、Web 管理后台、基础统计看板
V1 不含在线支付与收费活动、场地预约系统对接、活动直播与视频、原生 App 与 H5 完整适配、素质拓展学分自动认定、社团经费管理
后续规划活动评价与信用分、活动推荐（基于历史报名标签）、签到数据对接学工系统、活动相册与回顾
产品定位 V1 只做“发现 → 报名 → 到场 → 留痕”这条主链路。凡是不能强化这条链路的社交、内容、电商类需求，一律放到 V2 再评估。

03核心业务流程

3.1 活动生命周期

草稿 DRAFT→ 待审核 PENDING→ 已发布 PUBLISHED→ 进行中 ONGOING→ 已结束 FINISHED
待审核→ 已驳回 REJECTED→（修改后重新提交） 待审核
已发布 / 进行中→ 已取消 CANCELLED（组织者或管理员取消）
状态含义可执行操作操作者
草稿已创建未提交，仅本人可见编辑、删除、提交审核组织者
待审核已提交，等待审核员处理，学生端不可见撤回（回到草稿）、通过、驳回组织者 / 审核员
已驳回审核未通过，展示驳回理由编辑后重新提交组织者
已发布学生端可见，报名开放由报名时间控制编辑（需重新审核）、取消活动、查看名单组织者
进行中到达开始时间自动切换核销签到、补签、取消活动系统 / 组织者
已结束到达结束时间自动切换，报名关闭查看统计、导出名单、生成未到场名单系统 / 组织者
已取消活动不再举办，已报名用户收到通知查看取消原因组织者 / 管理员

状态由定时任务每 5 分钟扫描 start_time / end_time 自动推进，同时详情页读取时做一次惰性校正，避免任务延迟导致状态不一致。

3.2 报名流程

STEP 1
进入详情
校验登录态、活动状态、报名时间窗
STEP 2
填写表单
必填项校验，是否需审核决定后续状态
STEP 3
名额判定
条件更新占位；已满则入候补或直接拒绝
STEP 4
生成凭证
下发签到码，推送订阅消息

规则

  • 同一用户对同一活动只保留一条报名记录，唯一索引 uk_activity_user(activity_id, user_id) 兜底。取消后重新报名复用该行，重置状态与时间。
  • 报名时间窗由 signup_start_time 与 signup_end_time 控制，默认在活动开始时间结束报名，发布时可调。
  • 活动开启报名审核时，提交后状态为 待审核，组织者通过后转为 报名成功，容量在通过时占用。
  • 名额已满且开启候补时，状态为 候补中，记录 waitlist_seq 排队序号。
  • 有人取消报名，按候补序号顺序自动转正，推送通知；被转正者需在 24 小时内确认，超时顺延给下一位。
  • 取消报名默认截止到活动开始前 2 小时，发布时可按活动配置；已签到不可取消。
  • 报名表单支持 3 类自定义字段：单行文本、单选、多选，最多 5 个，答案以 JSON 存入 form_data。

3.3 签到流程

STEP 1
现场出示
组织者核销页展示动态签到二维码，30 秒刷新
STEP 2
学生扫码
微信扫一扫进入小程序签到页，携带 token
STEP 3
服务端校验
签名、时间窗、报名状态、（可选）定位距离
STEP 4
写入记录
幂等写入签到表，返回签到成功页

规则

  • 签到码 = 活动 ID + 时间片 + 随机数，服务端 HMAC-SHA256 签名，有效期 2 分钟，防止截图外传后被远程签到。
  • 签到时间窗默认“活动开始前 30 分钟 至 活动结束后 30 分钟”，发布时可配置，超出窗口提示不可签到。
  • 签到类型三选一：扫码、扫码 + 定位（场地 200 米内）、仅手动。定位签到失败时允许组织者手动补签。
  • 补签与核销必须记录操作人与原因，写入审计日志；同一报名记录只能签到一次。
  • 活动结束后未签到的报名记录批量标记为 未到场，供统计与后续信用机制使用。

3.4 活动审核流程

  1. 组织者提交后进入待审核队列，按提交时间排序，支持按组织、分类筛选。
  2. 审核员查看活动详情、组织者资质、场地与安全说明，可一键通过或驳回。
  3. 驳回必须选择理由标签（信息不全 / 场地冲突 / 内容违规 / 其他）并填写说明，组织者收到通知。
  4. 已发布活动修改关键字段（时间、场地、容量）需重新提交审核，修改简介、封面不触发。
  5. 审核员的每次操作写入 audit_record，保留操作人、时间、前后状态。

4.8 内容安全与风控（M8）

  • 活动标题、简介、详情、图片提交时调用微信内容安全接口（msgSecCheck / imgSecCheck），命中风险直接阻断并提示修改。
  • 报名接口按用户维度限流：10 秒内最多 5 次；签到接口按 openid 维度限流，防止脚本刷名额。
  • 活动封面与详情图只允许上传到自有对象存储，限制类型（jpg / png / webp）与大小（≤ 5 MB）。
  • 管理端登录失败 5 次锁定 10 分钟，操作需二次确认（下架、删除、解绑）。

6.3 关系说明

  • 一个组织有多个组织者（org_member），一个组织对应多个活动。
  • 活动对报名记录是一对多，报名记录对签到记录是一对一。
  • 用户对活动存在唯一报名记录与唯一收藏记录，均由唯一索引保证。
  • 所有业务表带 deleted 逻辑删除标记，MyBatis-Plus 全局配置生效；activity 统计字段用冗余列而非实时 count，避免列表页聚合查询。

07接口设计

7.1 通用约定

  • 风格：REST，前缀 /api/app（小程序）与 /api/admin（后台）。
  • 鉴权：请求头 Authorization: Bearer <token>，JWT 载荷含 userId 与 role。
  • 响应体：{ "code": 0, "message": "ok", "data": {...} }，业务异常统一 code ≠ 0，HTTP 状态码保持语义。
  • 分页参数：page（从 1 开始）、size（默认 10，上限 50），返回 records / total / page / size。
  • 错误码分段：10xxx 认证、20xxx 活动、30xxx 报名、40xxx 签到、50xxx 系统。

08非功能需求

8.1 性能与并发

项目要求
接口响应列表与详情接口 P95 ≤ 500 ms，报名与签到接口 P95 ≤ 800 ms（含三次数据库往返）
抢名额单活动瞬时 200 并发提交，最终成功数严格等于容量，不超卖、不重复
容量支撑 2 万注册用户、单学期 500 场活动、单活动 2000 人报名
首屏小程序首页冷启动到首屏可见 ≤ 2 s，活动列表分页 10 条/页

8.2 安全

  • 传输全站 HTTPS；JWT 密钥与微信 AppSecret 走环境变量，不进仓库。
  • 接口按角色鉴权，组织者资源做归属校验；所有写操作带当前用户上下文，禁止客户端传 userId。
  • 报名与签到接口幂等：客户端带请求 ID，服务端用唯一索引 + 幂等表双保险。
  • 敏感数据最小化：只采集学号、姓名、学院、年级、手机号，不采集身份证与家庭信息。
  • 后台账号密码 bcrypt 存储，登录与敏感操作写审计日志。

8.3 兼容与可用性

  • 小程序基础库 ≥ 3.0，覆盖微信 8.0 以上版本；iOS 与 Android 双端主流机型验证。
  • 后端单实例可运行，生产建议双实例 + Nginx 负载；数据库每日备份，保留 30 天。
  • 关键失败有降级：订阅消息失败降级为站内消息，统计接口超时返回缓存值。

8.4 合规

  • 首次登录展示隐私政策与用户协议，明确收集范围与用途，需勾选同意。
  • 提供账号注销与数据导出入口，注销后 30 天内清除个人信息，报名记录做匿名化保留。
  • 小程序类目按“教育 - 校园服务”提交，涉及活动发布需提供主体资质。

9.2 后端结构

campus-activity ├── activity-common 通用：统一响应、异常、工具、常量 ├── activity-domain 实体、DTO、VO、枚举 ├── activity-repository Mapper 与自定义 SQL ├── activity-service 业务逻辑：活动、报名、签到、统计 ├── activity-api 小程序端与后台端 Controller ├── activity-job 定时任务：状态推进、候补顺延、未到场标记 └── activity-admin 后台管理端（可选独立模块）

9.3 关键技术点

  • 登录链路：uni.login → code → 后端 code2session → openid → 查用户 → 未绑定学号则返回 needBind 标记 → 绑定后签发 JWT。
  • 名额占用：单条条件 UPDATE + 事务，不做“先查再插”；报名记录写入与计数更新同事务，失败回滚。
  • 签到码：HMAC(activityId + timeSlice + nonce, secret)，服务端只校验最近两个时间片，无需落库。
  • 状态推进：XXL-Job 或 Spring @Scheduled 每 5 分钟扫描，按 status + start_time 索引批量更新。
  • 分页：MyBatis-Plus PaginationInnerInterceptor 注册，单页上限 50 条，防止全表拉取。
  • 逻辑删除：全局配置 deleted 字段，唯一索引需带 deleted 或在取消时复用行，避免逻辑删除与唯一索引冲突。
