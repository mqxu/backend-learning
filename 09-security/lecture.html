00案例与问题

不是做“权限管理后台”，而是做一个小小的应用：学生交任务，教师批改，管理员管账号。

学生
提交与查看

提交实训任务，只能看到自己交的东西和自己的分数。

教师
批改

看到全班提交，打分写评语。学生交完立刻能看到。

管理员
账号

新增学生账号、停用账号，管理接口教师也进不去。

前端
四个页面

登录、我的提交、待批改、账号管理，按角色只显示该看到的菜单。

不用鉴权时，这个系统长这样就够跑了：接口直接暴露，谁拿到地址谁就能改分。教师能改，学生也能改；学生 A 改一下编号，就能看到 B 的评语。

本节要解决的是三件事，必须同时成立：

1
后端要知道“你是谁”

每个请求都得能查出调用者是 student01 还是 teacher01，不能靠前端自己说。

2
后端要知道“你能做什么”

学生不能批改，教师不能进管理接口，管理员两个都能做。

3
前端要知道“出事了怎么办”

没登录跳登录页，没权限只提示。这三件事没做好，接口再对，体验也是坏的。

本节的顺序

先看跑起来的效果，再一层一层拆开：登录拿令牌 → 后端认令牌 → 前端带令牌 → 按归属限数据 → 按权限点限操作 → 联调排错。每一层都能在浏览器和终端里当场验证。

02登录那一下发生了什么

整条链路只有两个动作：登录换令牌，然后每个请求带着令牌。先把这两个动作看清楚，后面所有代码都是围绕它们展开。

1
浏览器
POST /auth/login，提交用户名与明文密码（走 HTTPS 才安全）
2
AuthService
交给 AuthenticationManager 校验，BCrypt 比对密文、顺带检查账号是否停用
3
JwtTokenService
校验通过后签发令牌，写入用户名与有效期
4
浏览器
拿到令牌存起来，跳到首页；此后每个请求由拦截器自动加上请求头

后端这一侧的代码只有一句要记住：不自己比对密码。

Authentication authentication;

令牌里装了什么

把上面那个令牌拆成三段看。下面三段是真实值，你可以拿去任意 Base64 解码工具核对。

HEADER
eyJhbGciOiJIUzI1NiJ9
.
PAYLOAD
eyJpc3MiOiJiYWNrZW5kLWxlYXJuaW5nIiwic3ViIjoic3R1ZGVudDAxIiwiaWF0IjoxNzkzMTIxNDI4LCJleHAiOjE3OTMxMjg2MjgsInJvbGVzIjpbIlNUVURFTlQiXX0
.
SIGNATURE
共 43 个字符，由前两段加密钥算出，不能反推
第一段解码：{"alg":"HS256"}
第二段解码：{"iss":"backend-learning","sub":"student01","iat":1793121428,"exp":1793128628,"roles":["STUDENT"]}
字段含义为什么要有
sub用户名 student01后端靠它知道“你是谁”
exp过期时刻解析时自动校验，过期直接失败，不用自己写判断
iss签发方 backend-learning防止别的系统用同一个密钥签的令牌混进来
roles角色只给前端显示菜单用，不参与后端鉴权
两个必须当场讲清的点

载荷是明文，只是 Base64 编码，不是加密。任何人拿到令牌都能读到里面写了什么，所以密码、身份证号不能放进去。

角色放进去不等于用它鉴权。令牌签发后改不了，管理员把某人降级后，旧令牌里还写着 TEACHER。本模块的做法是令牌只带身份，权限每次请求按用户名回查数据库，改角色立刻生效。

前端存在哪里

存 localStorage，刷新页面不掉登录。三个函数就够，不需要为这点事引状态管理库：

const TOKEN_KEY = 'demo_token'
const USER_KEY = 'demo_user'

export const auth = reactive({
  token: localStorage.getItem(TOKEN_KEY) || '',
  user: JSON.parse(localStorage.getItem(USER_KEY) || 'null'),
})

export function saveLogin(data) {
  auth.token = data.token
  auth.user = { username: data.username, nickname: data.nickname, roles: data.roles }
  localStorage.setItem(TOKEN_KEY, data.token)
  localStorage.setItem(USER_KEY, JSON.stringify(auth.user))
}

export function clearLogin() {
  auth.token = ''
  auth.user = null
  localStorage.removeItem(TOKEN_KEY)
  localStorage.removeItem(USER_KEY)
}

为什么不存 cookie：令牌走请求头，浏览器不会自动带上，天然不受 CSRF 影响。代价是脚本能读到它，所以必须防 XSS，这是作业里要讨论的一条。

课堂验证

打开浏览器控制台执行 localStorage.getItem('demo_token')，能看到令牌；点右上角退出，再执行一次，返回 null。让学生亲眼看到“登录态就是一个字符串”。

03之后每个请求，后端怎么认出你

令牌只写身份，权限每次回库查，所以先得把数据放好。四张表，与 05-mybatis 共用一个库，表名加 sec_ 前缀避免冲突。

表关键列说明
sec_rolecode 唯一STUDENT / TEACHER / ADMIN
sec_userusername 唯一、password、enabled账号，密码存 BCrypt 密文
sec_user_role主键 (user_id, role_id)用户与角色多对多
sec_taskowner_id、status、score任务，归属指向 sec_user.id

两个设计点在课上值得说一句。归属存 id 不存用户名：用户名将来可能允许改，历史任务的提交人不能跟着变。权限点没建表：角色与用户的绑定是运行期数据，权限点是代码资产，跟着接口一起评审，放 Role 枚举里改一行就能 review 出影响面。

分层上的一条规矩

实体不出 service。User 只在 mapper 与 service 之间传，接口出参是 UserProfile，密码不可能顺着实体漏出去。安全层再隔一层 Account（用户 + 角色的领域对象），SecurityUser 就不必知道表结构。

拿到了令牌，请求头里带上 Authorization: Bearer eyJ...。后端要在进入 Controller 之前把它换成一个“已认证的身份”。这件事由一个自己写的过滤器完成。

→
请求进来
带 Authorization 请求头
1
JwtAuthenticationFilter
取请求头 → 验签 → 按用户名回查账号 → 写入 SecurityContext
2
AuthorizationFilter
判断这条 URL 要不要放行，此时身份已经在上下文里
3
Controller
@PreAuthorize 再看权限点，@AuthenticationPrincipal 直接拿到当前用户
public class JwtAuthenticationFilter extends OncePerRequestFilter {

    private static final String BEARER_PREFIX = "Bearer ";

    @Override
    protected void doFilterInternal(HttpServletRequest request, HttpServletResponse response,
                                    FilterChain filterChain) throws ServletException, IOException {
        String token = resolveToken(request);
        if (token != null && SecurityContextHolder.getContext().getAuthentication() == null) {
            String username = tokenService.parseUsername(token);   // 验签 + 校验过期与签发方
            UserDetails user = userDetailsService.loadUserByUsername(username);
            UsernamePasswordAuthenticationToken authentication =
                    new UsernamePasswordAuthenticationToken(user, null, user.getAuthorities());
            SecurityContextHolder.getContext().setAuthentication(authentication);
        } catch (JwtException | UsernameNotFoundException e) {
            // 令牌无效只清空上下文，不在这里写响应
            SecurityContextHolder.clearContext();
        }
        filterChain.doFilter(request, response);
    }
}

加进过滤链只有一行，位置很关键：

.addFilterBefore(jwtFilter, UsernamePasswordAuthenticationFilter.class)

必须排在授权判断之前。排后面的话，判断权限时 SecurityContext 还是空的，所有请求都会被当成未登录。

一个容易被问到的选择

令牌无效时不在这里返回 401，而是清空上下文继续往下走。让后面的授权判断拒绝这个匿名请求，401 由 RestAuthenticationEntryPoint 统一输出。要是在过滤器里也写一份响应，同一个错误就有两种格式，前端得写两套判断。

验证一下，两个请求的差别只有请求头：

# 不带令牌
curl -i http://localhost:8009/api/tasks/mine
# HTTP/1.1 401
# {"code":401,"data":null,"message":"未认证或令牌已失效"}

# 带上令牌
curl -H "Authorization: Bearer $TOKEN" http://localhost:8009/api/tasks/mine
# HTTP/1.1 200

04前端要做的三件事

这一节是前后端分离里学生最容易漏掉的部分：接口写完了，前端每个页面各写一遍 if (res.status === 401)，最后谁也不敢动。

做法是集中到一个文件 src/api/request.js，四个页面都不再关心鉴权。

请求拦截器：把令牌带上

const request = axios.create({ timeout: 10000 })

request.interceptors.request.use((config) => {
  if (auth.token) {
    config.headers.Authorization = `Bearer ${auth.token}`
  }
  return config
})

页面里写 await myTasks() 就够了，不用每次记得加请求头。登录接口本身没有令牌，if 判断自动跳过。

401 和 403 必须分开处理

401
没登录，或者登录过期

服务端不知道你是谁

触发
没带令牌 / 令牌过期 / 令牌被改
前端动作
清登录态，跳登录页，记住原来要去哪
403
登录了，但这件事你不能做

知道你是谁，权限不够

触发
学生调教师接口 / 看别人的数据
前端动作
只提示，绝不能把人踢下线

写反了会怎样：学生点了一个只有教师能点的按钮，直接被踢回登录页，重新登录进去还在那个页面，再点又被踢。学生只会觉得“系统坏了”。

request.interceptors.response.use(
  (response) => {
    // 业务失败也是 HTTP 200，靠 code 区分
    const body = response.data as ApiResult<unknown>
    if (body.code === 200) return body.data as never
    notify(body.message || '操作失败')
    return Promise.reject(new Error(body.message))
  },
  (error: AxiosError<ApiResult<unknown>>) => {
    const status = error.response?.status

    if (status === 401) {
      clearLogin()
      const from = router.currentRoute.value.fullPath
      router.push({ path: '/login', query: { redirect: from } })
      notify(error.response?.data?.message || '登录已失效，请重新登录')
    } else if (status === 403) {
      notify(error.response?.data?.message || '你没有权限做这个操作')   // 不动登录态
    } else if (status) {
      notify(`请求失败（${status}）`)
    } else {
      notify('连不上后端，确认 8009 是否已启动')
    }
    return Promise.reject(error)
  }
)
这里的两层判断要讲清

第一层是 HTTP 状态码，处理“没登录”“没权限”这类协议层的事；第二层是响应体里的 code，处理“任务已批改”“用户名已存在”这类业务失败。后端约定业务失败仍返回 200，所以少了第二层判断，业务错误会被当成成功。

类型怎么串起来

类型写在 src/types/api.ts，一条条对着后端的 vo 与 dto 核过。改后端字段时先改这里，npm run typecheck 会把所有用到的地方指出来。

export interface TaskView {
  id: number
  title: string
  owner: string
  status: TaskStatusCode            // 'SUBMITTED' | 'REVIEWED'
  statusText: string
  score: number | null              // 未批改时为空，不写 null 页面就会崩
  comment: string | null
  submittedAt: string
  reviewedAt: string | null
}

拦截器把 Result 拆成了 data，但 axios 的类型仍认为返回完整响应。只在 http 工具里收敛一次，页面里就都是实打实的类型：

async function unwrap<T>(promise: Promise<unknown>): Promise<T> {
  return (await promise) as T
}

export const http = {
  get: <T>(url: string) => unwrap<T>(request.get(url)),
  post: <T>(url: string, data?: unknown) => unwrap<T>(request.post(url, data)),
  del: <T>(url: string) => unwrap<T>(request.del(url)),
}

// 接口清单因此可以一行一个，返回值类型直接写在签名上
export const myTasks = () => http.get<TaskView[]>('/api/tasks/mine')
类型检查当成编译的一部分

npm run build 会先跑 vue-tsc --noEmit 再打包。字段名写错、少了 null 判断、角色名写错，在打包这一步就过不去，不用等浏览器里白屏才发现。

路由守卫：别让人手输地址进去

router.beforeEach((to) => {
  if (to.meta.public) return true

  if (!auth.token) {
    return { path: '/login', query: { redirect: to.fullPath } }
  }
  if (to.meta.roles && !hasAnyRole(to.meta.roles)) {
    return homeOf()          // 角色不对回自己的首页，不要踢回登录页
  }
  return true
})
必须强调的一句话

路由守卫只是体验层的拦截。有人改一下 localStorage 就能进页面，但进去以后接口全是 403，什么也拿不到。权限判断永远在后端，前端做的只是别让用户白点。

列表页的统计和筛选，先在前端算

学生页顶上四个数字（已提交、待批改、已批改、平均分），教师页那句"待批改 11 份"，都不是后端算的。列表接口一次给全量，页面上从同一个数组里算出来：

const stats = computed(() => {
  const reviewed = tasks.value.filter((task) => task.status === 'REVIEWED')
  const total = reviewed.reduce((sum, task) => sum + (task.score ?? 0), 0)
  return {
    total: tasks.value.length,
    pending: tasks.value.filter((task) => task.status === 'SUBMITTED').length,
    average: reviewed.length ? (total / reviewed.length).toFixed(1) : '—',
  }
})

// 筛选就是一次数组过滤，不发新请求
const visible = computed(() =>
  filter.value === 'ALL' ? tasks.value : tasks.value.filter((t) => t.status === filter.value),
)

这么写有两个好处：切筛选不闪、不加请求；后端不用为"统计"多开一个接口。代价是列表必须一次拿全，几百条以内没问题。

换成后端分页，这两件事都得跟着改

"平均分"不能拿当前页算，那不是全班平均分；筛选也不能只在本地做，第 2 页的数据根本不在手里。那时统计要单独出一个聚合接口，筛选条件要变成查询参数。代码里留了注释，讲的时候点一句就够。

05数据归属：最容易出事的地方

“学生只能看自己的”这句话，有三种实现方式，只有一种是对的。

做法前端怎么写后果
① 前端传用户名
错		 GET /api/tasks?owner=student01 把参数改成 student02 就能看别人的，后端等于没鉴权
② 路径里带用户名
错		 GET /api/tasks/mine/student01 改路径里的名字就行，一样能越权
③ 服务端从令牌取
对		 GET /api/tasks/mine URL 里没有身份，前端无处可改

代码就这么几行，关键在于参数是 SecurityUser 而不是从前端来的字符串：

/**
 * 我的提交：URL 里没有用户名，前端想查别人的也无从下手
 */
@GetMapping("/mine")
public Result<List<TaskView>> mine(@AuthenticationPrincipal SecurityUser user) {
    return Result.ok(taskService.listMine(user.id()));   // id 来自令牌，不是请求参数
}

提交任务时同理，请求体里根本没有 owner 字段。前端就算硬塞一个进去，也不会被采纳：

{"title":"实训四：伪造归属","content":"试试改 owner","owner":"student02"}

// 后端返回的
{"id":4,"owner":"student01","ownerNickname":"朱彦清","statusText":"待批改"}

这条已经写成测试用例 ownerCannotBeForgedByBody，跑 mvn test 就能验证。

换个编号就能看别人的详情，怎么办

详情接口 GET /api/tasks/{id} 的编号一定可以被改，所以必须在服务端判断“这条记录归不归你”：

public TaskView detail(Long id, SecurityUser viewer) {
    TaskRow row = findRow(id);
    if (!canView(row, viewer)) {
        throw new BusinessException(ErrorCode.FORBIDDEN);
    }
    return TaskView.of(row);
}

/**
 * 两种人能看：提交人本人，或者有批改权限的教师与管理员
 */
private boolean canView(TaskRow row, SecurityUser viewer) {
    if (row.getOwnerId().equals(viewer.id())) return true;
    return viewer.getAuthorities().stream()
            .anyMatch(authority -> authority.getAuthority().equals("task:review"));
}

实测（student01 的令牌，访问 student02 的任务）：

curl -i -H "Authorization: Bearer $STUDENT_TOKEN" http://localhost:8009/api/tasks/2
# HTTP/1.1 403
# {"code":403,"data":null,"message":"无权访问该资源"}
状态码必须是 403，不能是 200

很多项目把这类拒绝包装成 code: 500 或 code: 403 但 HTTP 200，前端拦截器会把响应当成成功处理，表格里就渲染出别人的数据。本模块在全局异常处理器里对越权单独给 403：

HttpStatus status = switch (e.getErrorCode()) {
    case FORBIDDEN -> HttpStatus.FORBIDDEN;
    case UNAUTHORIZED -> HttpStatus.UNAUTHORIZED;
    default -> HttpStatus.OK;      // 其余业务失败沿用 200 + code
};
return ResponseEntity.status(status).body(Result.fail(e.getErrorCode()));

06权限点：谁能做哪件事

三个角色，各自的权限点写在一个枚举里，一眼能看完：

public enum Role {
    STUDENT(Set.of("task:submit", "task:read")),
    TEACHER(Set.of("task:review", "task:read")),
    ADMIN(Set.of("user:read", "user:write", "task:read", "task:review"));
}
接口谁能调写法别人调的结果
POST /api/tasks学生hasAuthority('task:submit')教师 403
GET /api/tasks教师、管理员hasAuthority('task:review')学生 403
POST /api/tasks/{id}/review教师、管理员hasAuthority('task:review')学生 403
GET /api/tasks/mine登录即可不加注解，只查自己—
GET /admin/users管理员URL 规则 /admin/**教师 403

为什么接口绑权限点而不是绑角色：将来多一个“教务”，能看全部但不能批改，只要给角色配 task:read，接口代码一行都不用改。绑角色的话，每个 @PreAuthorize 都要改一遍。

两个必踩的坑

hasRole("ADMIN") 内部会拼成 ROLE_ADMIN 去比对，所以权限集合里要有 ROLE_ADMIN；hasAuthority("task:review") 是原样比对，不能加前缀。这两个混用，会出现“配置看起来是对的，却永远 403”。

管理接口做了双重把关：URL 规则 /admin/** 限管理员，Controller 上再写一次 @PreAuthorize。有人把 URL 规则改宽时，第二道还在。

课堂验证

用教师令牌调提交接口，用学生令牌调批改接口，两个都应该 403。再让教师点开“待批改”页面，页面上根本没有提交入口：前端不给入口，后端不给权限，两层都要做。

每个练习都在 5 到 8 分钟内完成，改完当场能看到结果。

练习一：让教师也能提交一条教学示范

现在教师调 POST /api/tasks 是 403。要求教师也能提交，但学生依旧不能批改。

参考答案

给 Role.TEACHER 加 task:submit，重启后教师就能提交。整个改动只碰一行枚举，接口代码没动，这正是权限点的价值。

顺便问一句：为什么不能直接把 @PreAuthorize 改成 hasAnyAuthority('task:submit','task:review')？能跑，但把“谁能提交”这条业务规则藏进了接口注解里，下次再变又要改代码。

练习二：让学生能撤回自己还没被批改的任务

加一个 DELETE /api/tasks/{id}，只有本人、且状态是“待批改”时才能删。

参考答案

Controller 只要求登录，把判断放进 Service：

@Transactional(rollbackFor = Exception.class)
public void withdraw(Long id, SecurityUser user) {
    Task task = taskMapper.selectById(id);
    if (task == null) {
        throw new BusinessException(ErrorCode.TASK_NOT_FOUND);
    }
    if (!task.getOwnerId().equals(user.id())) {
        throw new BusinessException(ErrorCode.FORBIDDEN);      // 不是本人的，403
    }
    if (task.getStatus() == TaskStatus.REVIEWED) {
        throw new BusinessException(ErrorCode.TASK_ALREADY_REVIEWED);
    }
    taskMapper.deleteById(id);
}

检查三点：学生删别人的要 403；删已批改的要给业务提示；教师没有 task:submit，是否允许教师删要明确写出来，别默认能删。

练习三：把令牌有效期改成 1 分钟

改配置 app.jwt.expire-minutes: 1，登录后用页面点几个操作，等一分钟再点，观察前端反应。

预期现象

一分钟后的第一个请求返回 401，拦截器清登录态并跳到登录页，登录后回到原来的页面。这条练完，学生就真正理解 401 和“刷新令牌”为什么存在。

11小结

整个模块其实只有六个动作，串起来就是一条完整链路：

1
登录换令牌

密码校验交给 AuthenticationManager，通过后签发 JWT，里面只有身份和有效期。

2
前端存令牌

存 localStorage，刷新页面不掉登录；退出就是清空。

3
每个请求带令牌

axios 请求拦截器统一加 Authorization，页面不用管。

4
后端过滤器认人

验签、查过期、按用户名回查账号，写进 SecurityContext，位置在授权判断之前。

5
按归属限数据，按权限点限操作

归属从令牌取，不看参数；操作看 hasAuthority，不看角色名。

6
前端分开处理 401 与 403

401 跳登录并记住来处，403 只提示，绝不踢下线。

三个可以被反复问到的判断

“为什么令牌里不放权限？” 令牌签发后改不了，降级不生效。放身份、回查权限，代价是每个请求多一次查询。

“前端守卫都做了，后端还要判吗？” 要。前端能被绕过，后端是唯一可信的一层。

“401 和 403 一定要分开吗？” 一定要。混在一起，学生点一个没权限的按钮就会被踢下线，体验是坏的。
