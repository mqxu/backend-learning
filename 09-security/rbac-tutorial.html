问题不在"他登录了没有"，而在"这条记录归不归他"。身份认证只回答第一个问题。授权要回答第二个，而 RBAC 负责的是更靠前的第三层问题：这类操作，这种身份的人到底允许做吗。


  

    三个层次，别混在一起
    
认证：你是谁（令牌解析）。功能授权：这个角色能不能调这个接口（RBAC 的主场）。数据授权：这条具体的记录归不归你（业务代码判定）。三层缺一层就是漏洞。

  







  
02三列模型：谁、什么角色、能干什么

  


  
RBAC 的全称是 Role-Based Access Control，基于角色的访问控制。主张只有一句：权限绑定在角色上，角色分配给用户。用户不直接持有权限，权限也不直接指向用户，角色是唯一的挂载点。


  

    

      
概念回答的问题在本模块里的样子

      
        
用户 User谁在访问sec_user，14 个账号

        
角色 Role他承担什么职责sec_role：STUDENT / TEACHER / ADMIN

        
权限 Permission对某个资源能做哪个动作task:review 这类权限点，共 5 个

        
用户角色关联谁有哪个职责sec_user_role，多对多

        
角色权限关联这个职责能做哪些事本模块省掉了这张表，权限点写在 Role 枚举里

      
    

  


  
五个概念构成两段多对多：用户 ↔ 角色、角色 ↔ 权限。多对多落进关系库，就是两张中间表。下一节的五张表由此而来。


  
下图是本模块的真实数据。点左列的用户看他的角色，点右列的权限点看谁能拿到它。


  

    

      
用户 → 角色 → 权限点点击任意节点

      

    

    

      

      
四个账号，三个角色，五个权限点。

    

  


  
多了角色这一层，改动成本就从"改 N 个人"降到"改一个角色的配置"。新来一位助教，给他 TEACHER 就行，不用逐个接口加白名单。


  

    权限点给接口用，角色给人看
    
接口上应该写 hasAuthority('task:review') 而不是 hasRole('TEACHER')。前者说的是"这件事允许被做"，后者说的是"这个人是谁"。将来教务也要批改时，给教务配上 task:review 即可，接口一行不用改。

  







  
03数据模型：五张表，两段多对多

  


  
把上一节的五个概念落进关系库，标准做法是三张基础表加两张关联表。基础表存实体本身，关联表存多对多关系，主键取两端 id 的组合，天然挡住重复绑定。


  

    

      
五表模型点任意表看职责与关联

      

    

    

      

      
三张基础表（用户、角色、权限）加两张关联表，串成两段多对多。

    

  


  

    

      
表类型存什么关键约束

      
        
sec_user基础登录名、密码密文、姓名、启用状态username 唯一

        
sec_role基础角色编码与显示名code 唯一

        
sec_permission基础权限点编码、名称、所属资源code 唯一，如 task:review

        
sec_user_role关联谁有哪个角色主键 (user_id, role_id)

        
sec_role_permission关联哪个角色能做哪些事主键 (role_id, permission_id)

      
    

  


  

    
标准五表 · DDL

    
-- 基础表：权限点单独成表，code 就是接口注解里要写的那个字符串
CREATE TABLE sec_permission (
    id    BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    code  VARCHAR(50)     NOT NULL,   -- task:read / task:review
    name  VARCHAR(50)     NOT NULL,
    PRIMARY KEY (id),
    UNIQUE KEY uk_perm_code (code)
);

-- 关联表一：用户与角色。主键是两列组合，同一个人不会被重复授予同一角色
CREATE TABLE sec_user_role (
    user_id BIGINT UNSIGNED NOT NULL,
    role_id BIGINT UNSIGNED NOT NULL,
    PRIMARY KEY (user_id, role_id),
    KEY idx_ur_role (role_id)            -- 反向查“哪些人持有这个角色”用得上
);

-- 关联表二：角色与权限。这张表在标准模型里有，本模块省掉了
CREATE TABLE sec_role_permission (
    role_id       BIGINT UNSIGNED NOT NULL,
    permission_id BIGINT UNSIGNED NOT NULL,
    PRIMARY KEY (role_id, permission_id),
    KEY idx_rp_perm (permission_id)
);

  


  
两张关联表都别用自增主键。组合主键本身就在表达业务约束：一个人对一个角色、一个角色对一个权限点，各只允许存在一条记录。加自增 id 反而要靠唯一索引去补这个约束，多此一举。至于反向外键上的普通索引，是为了按“权限点反查角色”“角色反查用户”这两类查询不扫全表。


  
本模块为什么只用两张表


  
09-security 里实际只建了 sec_user、sec_role、sec_user_role，sec_permission 与 sec_role_permission 没有建，权限点写在 Role 枚举里。这是有意的取舍，不是漏了：


  

    

      
判断维度放库（五表）放代码（本模块）

      
        
变化频率权限点常调整，运营随时改跟着接口一起变，一次提交改完

        
谁维护运营或管理员，通过后台界面开发，跟着代码评审

        
可追溯需要额外做变更审计表git log 就是审计记录

        
启动依赖依赖库里有配置，空库启动没有任何权限代码即配置，空库也能跑

        
适用规模权限点多、角色多、要按权限点检索权限点稳定在几十个以内

      
    

  


  
教学项目里权限点会随章节增删，放代码能保证 clone 下来就能跑。真实系统要支持运营后台配权限、要回答“谁能看这个菜单”，就得上齐全五张表。


  
补齐五张表要改的地方


  
把 Role.authorities() 换成一次 JOIN 查询即可，接口上的 hasAuthority('task:review') 一行都不用动。这正是权限点与角色分离的收益。


  

    
PermissionMapper.java · 一次查完两段多对多

    
@Select("""
        SELECT DISTINCT p.code
        FROM sec_user_role ur
        JOIN sec_role_permission rp ON rp.role_id = ur.role_id
        JOIN sec_permission p     ON p.id = rp.permission_id
        WHERE ur.user_id = #{userId}
        """)
List<String> selectPermissionCodes(@Param("userId") Long userId);

  


  
    
    
  • 登录时先按用户查角色编码（ROLE_XXX 仍要拼），再查一次权限点编码，两者合并成 GrantedAuthority 集合。
    • 
    
  • 权限点变更后要让旧令牌失效，否则用户会拿着过期的权限集合继续访问。做法是给令牌加版本号，或者权限变更时清掉该用户的令牌。
    • 
    
  • 关联表的写入要包在事务里，先删后插或按差异增删，别留下半个角色的脏数据。
    •

04权限点怎么命名

  


  
约定是 资源:动作，全小写，冒号分隔。名字要在接口上直接读得通：hasAuthority('task:review') 念出来就是"有批改任务的权限"。


  
    
    
  • 用资源不用 URL。task:read 比 api:tasks:get 稳，接口改路径时权限点不用动。
    • 
    
  • 动作选动词，别用 CRUD 缩写糊弄。task:review 说明业务意图，task:update 说明不了。
    • 
    
  • 一个权限点对应一类操作，不要写成 task:read:all 这种复合含义。
    • 
  


  

    
练一下需求是"教务能看全部提交，也能批改，但不能提交任务"。下面哪种做法改动最小？

    

      
      
      
    

    
对。接口上写的是权限点，加一个角色就够了，接口代码不动。这正是把角色和权限点分开的收益。

  







  
05权限集合怎么摊平

  


  
Spring Security 里没有"角色集合"这个概念，它只认一个扁平字符串集合 Collection<GrantedAuthority>。所以登录成功后要把角色摊平：每个角色贡献两条东西，角色名本身 ROLE_XXX，以及它名下的全部权限点。


  
权限点的来源两种模型不同：五表模型下是上面那条 JOIN 查出来的 p.code 集合；本模块省掉两张表，直接读 Role 枚举的 permissions()。摊平这一步的产物一样，都是 List<String>。


  

    
Role.java · 摊平逻辑

    
public static List<String> authorities(Collection<Role> roles) {
    return roles.stream()
            .flatMap(role -> Stream.concat(
                    Stream.of(role.authority()),          // ROLE_TEACHER
                    role.permissions().stream()))         // task:review、task:read
            .distinct()                                   // 多个角色重复的权限点只留一份
            .toList();
}

  


  
下面这个计算器用的就是同一份数据。勾选角色，看摊平结果和接口可达性。故意勾两个角色，能看到并集和去重。


  

    

      
GrantedAuthority 计算器可多选

      

        
        
        
      

    

    

      

    

  


  

    ROLE_ 前缀是 Security 补的
    
hasRole("ADMIN") 内部比对的是 ROLE_ADMIN。所以在枚举里存角色名、摊平时手动加前缀，配置里绝不要写成 hasRole("ROLE_ADMIN")，那样会去找 ROLE_ROLE_ADMIN，永远为假。

  







  
06一次请求的判定路径

  


  
令牌带上来以后，请求要过四道关。任何一道不过，后面的都不再执行。


  

    
过滤器链顺序

    
CorsFilter
  ↓
JwtAuthenticationFilter        // 解析令牌，填 SecurityContext。失败不抛异常，留给后面的关判断
  ↓
ExceptionTranslationFilter     // 把 AuthenticationException 变 401、AccessDeniedException 变 403
  ↓
AuthorizationFilter            // 消费 authorizeHttpRequests 里的 URL 规则
  ↓
DispatcherServlet → Controller // 方法级 @PreAuthorize 由 AOP 拦截，抛 AccessDeniedException
  ↓
Service                        // 数据归属判断，业务自己写

    401 和 403 的分界
    
    不知道你是谁，给 401，前端清空令牌跳登录页。知道你是谁但不许做，给 403，前端只提示无权限，不要跳登录，否则用户刚登录就被踢出去，说不清。
    
  
    

    



    
  
    07数据级授权
    
  
    

  
    RBAC 只能管到"这类操作能不能做"，管不到"这条记录归不归你"。后者必须在拿到数据之后判断。
    

  
    
    
    TaskService.java · 归属判定
    
    
    private boolean canView(TaskRow row, SecurityUser viewer) {
    if (row.getOwnerId().equals(viewer.id())) {
        return true;                       // 本人
    }
    return viewer.getAuthorities().stream()
            .anyMatch(a -> a.getAuthority().equals("task:review"));  // 或教师与管理员
}
    
  
    

  
    下面四条记录，切换查看者，看谁能看哪条。student02 的提交就是给越权演示用的。
    

  
    
    
    
      
    归属判定GET /api/tasks/{id}
    
      
    
        
        
        
        
      
    
    
    
    
    
      
    
        
    
          
    id标题提交人这条能不能看服务端的判断理由
    
          
        
    
      
    
    
    
  
    

  
    
    归属只能由服务端按令牌判定
    
    提交接口的 owner_id 从令牌里的用户 id 取，不从请求体取，也不从前端传。前端传什么都不可信。这是本模块最重要的一条规矩。
    
  
    

    



    
  
    08三种常见反模式
    
  
    

  
    同一个需求，两种写法。切换对比，左边是把角色名写进注解，右边只认权限点。
    

  
    
    
    
      
    同一需求，两种写法
    
      
    
        
        
      
    
    
    
    
    
      
    
        
    
          
    把角色名硬编码进判断
    
          
    @PreAuthorize("hasRole('TEACHER') or hasRole('ADMIN')")
public Result<List<TaskView>> all() { ... }
    
        
    
        
    教务要批改时，得回来改注解。两处、三处、最后散在十几个 Controller 里，评审时看不出哪些接口受影响。
    
      
    
      
    
        
    
          
    只认权限点
    
          
    @PreAuthorize("hasAuthority('task:review')")
public Result<List<TaskView>> all() { ... }
    
        
    
        
    加角色只改 Role 枚举一行，所有相关接口自动生效，也没有接口上的字符串要跟着改。
    
      
    
    
    
  
    

  
    另外两种
    
  
    
    
    
      
    反模式表现后果与改法
    
      
        
    
          只在前端藏按钮
          前端 v-if="isAdmin" 藏了入口，后端接口不做校验
          改 URL 或拿 Postman 直接调就绕过了。前端隐藏只影响体验，不构成防线
        
    
        
    
          用角色名做数据过滤
          if (user.isTeacher()) queryAll() else queryMine()
          查询范围按角色分叉，越权面随角色数量膨胀。改成按归属与权限点判断，见上一节
        
    
        
    
          把越权藏在 200 里
          数据越权返回 HTTP 200 + 业务码
          前端拦截器会当成成功响应处理。本模块对越权返回真实 403，其余业务错误才用 200 + code

    10落地检查清单
    
  
    

  
    
    
    
      
    检查项本模块的做法
    
      
        
    三张基础表sec_user、sec_role 已建；sec_permission 暂由 Role 枚举承担
    
        
    两张关联表sec_user_role 已建；sec_role_permission 在补齐五表时加，主键取两端 id 组合
    
        
    登录接口放行/auth/login 与 /public/** 走 permitAll()
    
        
    规则从具体到宽泛anyRequest() 一定放最后，否则前面全部失效
    
        
    接口写权限点不写角色hasAuthority('task:review')，管理员另有 hasRole('ADMIN') 管整组管理接口
    
        
    双重把关/admin/** 一边 URL 规则、一边类上的 @PreAuthorize；写操作再加 user:write
    
        
    401 与 403 分开认证失败给 401 并清令牌，授权失败给 403 只提示
    
        
    归属服务端判定owner_id 从令牌取，URL 里的 id 只能当查询条件
    
        
    越权不打 200 折扣业务异常映射成真实 403，别让前端把拒绝当成功
    
        
    权限点有测试覆盖SecurityApiTest 里每个角色对每个接口的期望状态码都断言一遍
    
          
    
    
  
    

  
    回到开头那个改 id 的请求。现在它会在第三层被拦住，日志里留下一行 student01 试图查看 student02 的任务 2。这条日志本身也是资产，它告诉你有人在探边界。
